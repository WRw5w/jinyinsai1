# 2026-09-18

## 引擎部署加固：静态链接、线程数、依赖（承接 09-17 的 fast6 并行优化）

用户问「升级之后会怎么样」→ 把 fast6 作为默认引擎会发生什么的完整清单，顺手做掉了一个
真实的部署风险。

### 1. 发现的依赖差异
扫二进制导入串：`fast` / `fast4` 只导入 libstdc++、libgcc；**`fast6`（含 `-fopenmp`）多导入
`libgomp` + `libwinpthread`**。裸 PATH 实测：fast4 和 fast6 都报
`error while loading shared libraries: libstdc++-6.dll` —— 说明**这不是 fast6 引入的新问题**，
fast4 早就有（都在 `msys64/ucrt64/bin`，能跑 fast4 就能跑 fast6）。

### 2. 用 `-fopenmp -static` 把依赖清零
3.29 MB，**不再导入任何 libstdc++/libgcc/libgomp/libwinpthread**，裸 PATH 下 `exit=0`。
代价（best of 3，5s 墙钟，相对 fast4 串行）：

| 线程 | 1 | 4 | 8 |
|---|---|---|---|
| 动态 | ~1.00x | 2.02x | 1.86x |
| 静态 | ~1.00x | 2.01x | 1.71x |

→ **静态版已扶正为 `calibrated_knife_hunt_fast6.exe`**，动态版留作
`calibrated_knife_hunt_fast6_dyn.exe`。扶正后 N=5000/20000 × `KH_THREADS=1/4/8` 与 fast4 逐字节一致。

### 3. 线程数：建议 4，不是 8
多次重测 4 线程稳定优于 8（2.02x vs 1.86x）。只有 8 个 trial，且这台虚拟化机器线程越多越吃调度噪声。

### 4. 内存（峰值 RSS，20s 轮询工作集）
fast4 35.2 MB → fast6 4 线程 48.4 MB → 8 线程 56.3 MB。约 3.3 MB/线程，**有界**。

### 5. 构建脚本
`build_kernels.py`：编译 4 个内核（fast / fast4 / fast6 静态 / fast6 动态）+ 自带字节一致性回归，
不一致即 `exit 1`。
**⚠️ 这个沙箱跑不了 `.sh`**：嵌套 `bash <script>` 会去拉 `wsl.exe`（在 Program Blacklist 上），
直接 `PROGRAM BLOCKED BY SECURITY POLICY`。**脚本一律写 `.py`**（`bench.sh`、`build_kernels.sh`
都是因此改写的）—— 这个坑之前踩过一次，这次又踩了，已写进技能。

### 6. 升级到 fast6 的完整影响清单（回答用户的问题）
| 维度 | 会怎么样 |
|---|---|
| 已提交的包 | **不受影响**（ZIP 只含一个 JSON，评分方不跑引擎） |
| 历史导出 | **会变**（fast6 ≡ fast4，**不**≡ 驱动当前默认的 `fast`） |
| 同预算得分 | 120 s 下 **≈ +0.0010**（交错 A/B 复测，见下；早前写的 +0.003~+0.004 已作废） |
| 确定性 | 不变，任意线程数/调度逐字节一致 |
| 机器依赖 | 归零（静态版）；`-march=native` 仍本机专属，换 CPU 需重编 |
| 内存 | +13 ~ +21 MB，有界 |
| CPU | 单进程占 4–8 核；**与「6 进程并发跑 seed」互斥，必须显式 `KH_THREADS=1`** |
| 单核机器 | 不退化（`KH_THREADS=1` = fast4 的 1.01x），可无条件退回 fast4 |

## 「29158 卡死」结案 —— 一个假故障（2026-09-18 晚）

**结论：引擎从未卡死，驱动从未受影响。** 曾以为 fast4/fast6 被 Python `subprocess` + 管道
stdout 启动时会冻结在 `attempts=29158 accepted=100`（6/6 复现），并据此怀疑过 in-loop `save()`。

### 真相：读错了日志行
`calibrated_knife_hunt_fast4.cpp` 有两处 `attempts=` 打印：
- `:193` 循环内，`accepted` **首次**达到 100 时一次 → **恒为 `attempts=29158 accepted=100 knives=89990`**
- `:196` 循环后，带 **`FINAL`** 前缀 → 真实总数

seed 固定则搜索确定性，fast5/fast6 又与 fast4 逐字节一致 ⇒ 那条里程碑行在任何预算/线程数/
构建下**完全相同**。旧探针用 `re.search()`（第一条匹配）⇒ 永远读到它 ⇒ 看起来"冻结"。
短预算（accepted<100 就结束）只打印 FINAL，所以 5/10 s 看着正常、15 s+ 看着冻结。

30 s 一次运行两行都在：
`mid attempts=29158 accepted=100` / `FINAL attempts=49224 accepted=167`。

### 排除掉的假设（都实测过）
- **不是 `save()`**：去掉循环内 save（`dbg/f4_nosave.exe`）→ 仍 29158；只有**连日志一起去掉**
  （`f4_nolog.exe`）才读到 FINAL 45742/47871 —— 那只是因为没别的行可读。
- **不是 launch style**：piped/capture/inherit 一致。`inherit` 组"看着正常"是因为没捕获 stdout，
  控制台上那行 `FINAL attempts=46396` 被误记到它名下。
- **不是 CPU 抢抢**（我此前的错误归因）：固定工作量 35000 次 13 s 跑完、accepted=116，无死路。

### 驱动为何没事
`calibrated_knife_hunt_fixed.py:114` 用**继承 stdout**（不捕获）启动引擎，`:115` 直接读
**输出文件** `engine_output.txt`，从不解析 stdout ⇒ 只坑探针，不坑产线 ⇒ §18 端到端分数仍有效。

### 修正后的吞吐（首次用 FINAL 行读，20 s）
fast4-1t 1656 att/s ＝ 1.00x；fast4-4t 1581（0.95x，本就串行）；fast6-1t 1869（1.13x，噪声）；
**fast6-4t 3665 ＝ 2.21x**；fast6-8t 3387 ＝ 2.04x。**2.0–2.2x 结论站得住**。

### 另一颗地雷：驱动默认 `--initial` 是错的起点
跑端到端**必须显式 `--initial runs/khfast_smoke/result.json`**。默认的
`runs/calibrated_initial/result.json` 是另一条更弱初始方案：20 s 下 `score_capped` 98.8504
（yield 0.96181）vs canonical 98.9732（0.96577），**差 0.12 分**，极易误读成"引擎回归"。
canonical 见 `runs/speed2/verify.py:81-83`。

### 教训
**"整数重复"不等于测量被干扰 —— 先确认你读的是哪一行。** 我把它当成"后台基准抢 CPU"，
于是日志解析 bug 被写成"测量污染"，方向完全错了。
新建 `runs/speed2/enginelog.py`（`final(stdout)`，唯一正确读法）；`ladder.py`/`stallprobe.py`/
`isolate_stall.py`/`ab_engine.py`/`dbg/test_nosave.py` 全部改读 FINAL 行并保留误报说明。

## fast6 真实收益的定论：≈ +0.0010 分（不是 +0.003~+0.004）

用**交错 A/B**（`runs/speed2/ab_e2e.py`：2 seed × 2 重复，A,B,A,B，fast6 = `KH_THREADS=4`，
canonical `--initial runs/khfast_smoke/result.json`）复测 120 s：

| seed | fast4 (1x) | fast6 (≈2.2x) | Δ |
|---|---|---|---|
| 7411 | 98.97510589 | 98.97621498 | **+0.00111** |
| 5203 | 98.97570903 | 98.97662967 | **+0.00092** |

**fast4 两次重复极差仅 4e-05**（几乎完全可复现），所以 +0.0010 是它的约 25 倍，不是噪声。
我的 fast4 数值与存档的 `e2e120_v2`/`e2e120b_v2`（98.97508671 / 98.97571914）**逐位吻合**。

### 旧数字 +0.003~+0.004 为什么虚高（已作废）
逐条回溯：09-17 `e2e120.log` = 98.97684180/98.97987079（Δ+0.00303）；
`e2e120b.log` = 98.97594884/98.98024277（Δ+0.00429）；09-18 v2 = +0.00138 / +0.00181。
根因是**臂序偏置**：`verify.py:117-119` **先跑 fast6、后跑 fast4**，尾随负载（编译残留、
后台进程、上一进程收尾）全落在**基准臂**上 → 压低 fast4、抬高 Δ。09-17 两组的 fast4 基线
（98.97684/98.97595）本身就比之后任何一次都高，印证了这一点。
**规则：测 A/B 要么交错，要么至少让基准臂先跑，且确认无并发负载。**

### 顺带收回"预算越长收益越大"
45 s +0.00157 vs 120 s +0.0010，差异在噪声内。收益小的真因是 **yield 对 attempts 强凹**：
0.965774459579@29158 → 0.965788529113@49224 → 0.965794150166@74989，
29158→49224 换 +1.40e-05，49224→74989 只换 +0.57e-05。

### 教训补充
**测量顺序本身就是一种系统性偏差。** 顺带发现跑端到端必须显式传 canonical `--initial`。
