## 「能不能写 GPU 加速」调研：规则层面无禁区，但引擎瓶颈在 CPU 排序，GPU 无收益

### 规则审计（`棒材组合订单高效锯切优化-4.pdf`，用 `pdftotext -layout` 提取到 `tmp/rules.txt`）

全文检索 `并行 / 线程 / 多进程 / 分布式 / GPU / 算力` **命中 0 次** —— 规则对并行计算**无字面允许也无禁止**。
只有五条间接条款：
- 五(三) 单批次求解时间 ≤10s、平均求解时间占 10% → 间接激励并行；
- 八(二) 硬件环境：**32 核心 CPU / 32GB 内存 / 显存 24G** → 最接近「事实性授权」；
- 十一(一) 允许开源库与框架（NumPy/Pandas/Matplotlib/Geatpy 等等）→ 开放列举，未点名并行/GPU 库；
- 十一(二) 求解器仅限自研或开源，商业求解器**只许 COPT** → 唯一硬边界；
- 九 2.a 「无平台依赖」才满分 → CUDA/闭源运行时是主观分风险。
另：**PDF 第九节的公式 `40*成材率` 与同段「成材率占 30%」自相矛盾，是文档笔误**；
四份官方反馈一致支持 40/30/20/10，以我们的校准为准。
数据包内只有 `constraints.txt`（4 条物理约束）+ 两个 CSV，无额外环境说明。

### 引擎热点剖析（`bench_profile.exe`，15s，beam 48，输入 `runs/kh5a/engine_input.txt`）

```
attempts=13643 trials=109144 levels=472332 options=5150375 expansions=94821844
sortSeconds=8.81 / 15.0 wall = 58.8%   setDedupSec=2.76 = 18%
sorts=269568  sortedItems=92113150  perSort avgItems=341.7
```
**~77% 的墙钟时间花在给 ~342 元素的数组排序 + 用 `std::set` 去重**，算术本身几乎免费。
原因：每次尝试要做 8 个 trial，每 trial 在 ≤24 个订单层上做 beam=48 的 DP，
每层 `next.size()` 达 `beam×options` 后 `std::sort` + 红黑树去重。

### 对照实验：`bench_hashdedup.cpp`（bucketed 生成戳表 + nth_element 替代 sort+set）

桶键 `(int(l1*2), int(l2*2))` 上界 2×148=296 → 用 512×512 直接索引表 + generation stamp，
一趟 O(n) 求出每桶最小 rank，再 `nth_element` 选 top-beam。保留语义与原版一致
（原版「rank 序中首个出现的同桶状态」即该桶最小 rank）。

固定 `KH_MAX_ATTEMPTS=20000`、seed 9106、beam 48，各跑 3 次取中位数：

| 版本 | 中位耗时 | 相对 | 结果 |
|---|---|---|---|
| 基线 `sort`+`set` | **22.15 s** | 1.00× | accepted=287, yield=95.8723% |
| `bench_hashdedup` | **15.20 s** | **1.46×** | accepted=330, yield=95.8785% |

注意两者**不是逐位等价**（nth_element 的并列打破方式不同 → 轨迹分叉），只能做统计比较；
但要正确性对拍应比较 keep 集合而非轨迹。产物：`tmp/prof/{base_mine,hashdedup}.exe`。
**结论：GPU 对本引擎无效**（顺序马尔可夫链 + 24×48 的极小 DP，kernel 启动开销远超计算量）；
真正的加速空间是 CPU 侧的 O(n log n)→O(n)。

### GPU 不适合的定量判据（由上面剖析数据推出，后续别再重复论证）

- 并行度上限：可拆出的独立单元 = 钢种×直径组数 = **22** → 占用率约 1%。
- 单工作单元：`expansions/levels = 94821844/472332 ≈ 200 次状态更新/层`（48 lane × ~4 有效选项），
  而一次 CUDA kernel 启动 3–10 µs > 该层全部有用功；且 472K 层因层间依赖不能合并。
- 算术强度：94.8M 扩展 × ~15 flop ≈ 1.4 GFLOP / 15 s ≈ **95 MFLOP/s**，与 GPU 的几十 TFLOPS 差约 10^6 倍。
- 工作集：4999 订单 × ~100 B ≈ 0.5 MB，常驻 L2 → GPU 的显存带宽优势完全用不上。
- 关键澄清：**「GPU 不适合」≠「并行没用」**。CPU 多进程多起点是可用的（`runs/kh5*` 12 路已试），
  但那是多起点不是多算力，边际收益递减——12 路全部收敛到 89393–89400。
- 若将来真要上 GPU，唯一站得住的形态是**换算法**：列生成 / 大规模候选切割模式枚举（10^8–10^12 列）
  或批量枚举候选批次一起打分，而不是把现有引擎翻成 CUDA。

### 残差的来源与唯一解法

L3 包逐坯型申报 `ceil(A_bt / BW_bt)`，所以 `raw − A = Σ_bt (ceil(A_bt/BW_bt)·BW_bt − A_bt)`
是**纯 ceil 取整余量**。

**BW = {1: 9613.5, 2: 6162.5}**（整半数值，很好记）⇒ `raw` 只能落在
**gcd(2·9613.5, 2·6162.5)/2 = 246.5 kg 的格点**上。`ceil` 只向上取整，
所以唯一动作是**把 `A_bt` 从下方顶到格点**。
⚠️ 越过格点 → `ceil` 跳一整个坯重（9.6 t / 6.2 t），残差从几 kg 炸到近万 kg。**必须严格从下方逼近。**

### 免费质量从哪来（关键洞察，可复用到任何同类题）

`entry_knives = max(2, int(L // size) + 1)`，包内长度写成 `k·size·(1-1e-12)`
使 float 的 `L // size` 落到 `k−1`：

| k | int(L//size)+1 | entry_knives |
|---|---|---|
| 1 | 1 | **2**（max 抬起） |
| 2 | 2 | **2** |
| ≥3 | k | k |

⇒ **k=1 与 k=2 都计 2 刀；给 k=1 的段加 1 支是零刀数代价的。** L3 包有 1357 个 k=1 段。

## 搜索内核提速第二轮（fast4，2.35x）

### 9. 结论

`calibrated_knife_hunt_fast4.cpp` / `.exe`：**2,088 次尝试/秒 = 原始 `fixed` 的 2.35x、
上一代 `fast` 的 1.61x**（12 s 固定墙钟 ×3 轮取最好）。同样 45 s 端到端跑完整驱动管线：

98.97331437937274），`platform_check` 两者都 passed=true。**同样时间、同样合法、fast4 方案更好。**

### 10. 纠正一个被写进文档的错误假设（重要）

上一轮遗留的「下一步」写着：*307 个候选只落进约 54 个 bucket，排序规模降 ~5.7x*。
**这是错的。** 加桶计数实测：`avgSortItems=305.0` → `avgBuckets=186.2`，**只压缩 1.64x**。
于是「先去重再排序」（`fast2`）几乎没有收益（吞吐 1,298 → 1,353，仅 +4%），保留仅作对照。

fast4 真正有效的三件事：
1. **候选评估不构造 `Row`**：原来 beam 里每个状态都为了打分建两个 `Row`（各带一个 `vector`），
   改成直接从状态算 `Tot`，只给胜者建 `Row`。单次 ~180 µs → 17 µs。
2. **`nth_element` 部分选择替代全排序**：候选记录缩成 16 B `{double r;int i;int k;}`，bucket key
   走旁路数组。**`(rank,index)` 是严格全序 ⇒「最小的 `beam` 个幸存者」是良定义集合，
   部分选择返回与全排序完全相同的前缀**。排序 352 µs → 109 µs。
3. **哈希不追指针**：刀数 `k` 放进 16 B 候选记录，并列比较不再随机访问 120 B 的 `State` 数组。

分布：扩展 32.2%→40.6%、排序 40.2%→20.0%、去重 6.9%→20.5%（哈希）、other 20.6%→15.8%。

### 11. fast4 为什么做不到逐位等价（关键认知）

`-DXCHECK` 交叉校验（并行跑旧/新归约并逐字段比对幸存状态）：幸存者**数量永远相同**，
但**代表选择约 64% 不同**；差异全在同一 bucket 内 —— `fDiff` 仅 **0.8%**，`kDiff` 达 **64%**。
根因：`scoring_mu` 全场一致 ⇒ `f` 被 `(l1,l2)` 唯一确定 ⇒ **同一 bucket 的成员 `rank` 全都相等**，
旧引擎取 `std::sort` 的第一个，而 introsort 对相等元素的排列不可复刻（改「最小 index」仍 65% 不匹配）。

**但这不是 bug**：桶内成员成材率等价，只有刀数与切法不同。fast4 用规范代表
**`rank` 最小 → 刀数最少 → index 最小**，确定的，且从不比旧引擎多花刀（所以同工作量下
accepted 254→420、成材率反而更高）。

**因此验收标准从「逐字节等价」改成三层**：
① `fast3` vs `fast4` 逐字节（3k/20k/60k 全 IDENTICAL，验证第 2 项是恒等重构）；
② 同工作量质量不劣（实测更优）；③ 同 seed 同工作量两遍 md5 一致；④ 端到端 `platform_check` passed。

## 第三轮：并行优化（fast6 = 再 2.1x，≈ 原始引擎 4.9x）—— 用户问「能不能做工程优化，例如并行」

### 15. 关键诊断（两个假设，一否一证）
- ❌ 不是 worker 唤醒延迟：OMP_WAIT_POLICY=ACTIVE + GOMP_SPINCOUNT=3e7 只多买 3–10%。
- ✅ 是每次尝试的并行区 fork/join：空并行区进出 1 线程 2.8us → 6 线程 117us → 8 线程 198us，

  放并行区体的普通局部变量即可。
