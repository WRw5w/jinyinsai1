## 任务 #5 卡死根因定位与修复（关键！）

**现象**：全量首跑在 `chunks/NP01_43.0/000360.json` 之后 **66 分钟零产出**，进程存活、日志 0 字节
（`runs/semi_nolimit_v1`，PID 36392，215MB）——是卡住不是崩溃（OOM 会约 4.8GB）。

**定位手段**（可复用）：新建 `diagnostics/hang_chunk.py`，按 solve_semi 顺序逐 chunk 重放
`pick_group(all_orders,'NP01:43')`，用 `faulthandler.dump_traceback_later(LIMIT, exit=True)`
在窗口到期后打印**全部线程栈**并强退。注意：
- `ROOT = Path(__file__).resolve().parent.parent`（否则 `ModuleNotFoundError: solver`）。
- 必须用工具 `run_in_background=true` 跑（bash 默认 120s 超时会 SIGTERM 掉它）。
- 复现结论：单独跑 chunk@420 只要 35.1s，但**顺序重放时 @420 卡死 >60s** ⇒ 与同进程累积状态相关。

**栈输出**（决定性）：
```
File "solver.py", line 1164 in _enumerate_round_shapes
File "solver.py", line 1093 in _round_moves
File "solver.py", line 1313 in _closing_rounds
File "solver.py", line 1028 in _construct
File "solver.py", line 1880 in search_10s
```

**根因**：`_SHAPE_CAP = 4000` **声明了却从未被读取**——`_enumerate_round_shapes` 里的
`itertools.product` 是**完全无界穷举**，且该函数从头到尾**不看 `deadline`**（它是惰性缓存入口，
设计上被刻意做成 deadline-free）。复赛最宽几何单元 `max_seg=42`（3.6m 定尺，150m 床长-1m 切头），
两规格组 `42×42×plimit`，三规格组 `42³×50`≈370 万次 `offer` 探测。因为 seeding 被明确定义为
**不可中断**（clause 12 要求每个订单都有方案），调用方的超时包不住它 ⇒ 全量跑必然僵死。
（`itertools.product` 会在中途持续 yield，所以构造阶段内存也不炸，纯粹是 CPU 自旋。）

**修复**（`solver.py`）：
- 新增 `_SHAPE_WORK_LIMIT = 300000`（探测预算）+ `_SHAPE_WORK_STRIDE = 8192`（按 stride 检查，
  避免每轮读 `time.perf_counter` 把便宜迭代的成本翻倍）。
- `_enumerate_round_shapes`：`offer()` 内 `probes += 1`；product 循环里 `counter % STRIDE == 0
  and probes > LIMIT` 即 `truncated = True; break`（外层 parallel 也 break）。
- 把 `_SHAPE_CAP` 真正接进 Pareto 剪枝入口：`if len(best) <= _SHAPE_CAP or truncated:` 才做阶梯剪枝，
  否则 else 分支直接交出全部探测到的 moves（`_MOVE_CAP` 本来就会再裁 4000）。
- 注释写明**截断为何安全**：单一订单最大形状在 product 之前就已 `offer`，故截断集合仍保有收尾搜索
  最依赖的形状；收尾失败只是丢该候选，贪心的轮次仍合法完整。

**验证**：清空缓存从 @0 重跑 `diagnostics/hang_chunk.py 600 0`：
@0-@360 缓存命中，**@420 = 20.07s（修复前自旋 >66min）**，@480–@900 稳定 20.1–21.3s/块。
`python -m unittest test_solver` 10/10 通过（含 `test_matches_unpruned_oracle`，证明剪枝行为未破坏）。
