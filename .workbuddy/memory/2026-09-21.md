## 核心发现：`_closing_rounds` 是唯一的成本黑洞

插桩诊断（`tmp/instr_c60.py` 手法：monkey-patch 后统计 calls/time）：

- **成功对**：`_construct` 1.2~3.2s，`_closing_rounds` 全部返回正解
- **失败对**：`_construct` 2~13.4s，其中 >95% 时间在 `_closing_rounds`，且**全部返回 None**
- `_solo_scheme` 是 O(n×p) 直构，**0.00s**，从不是瓶颈

### 之前的两个 cap 都不够

`_CLOSING_NODE_LIMIT`（总状态数）和 `_CLOSING_STATE_CAP`（每层状态数）都只约束**状态数量**，不约束**产生它们的比较次数**。BFS 每层是 `len(prev_states) × len(moves)` 的乘积，`(840,1399)` 的实测：637 → 8416 → 7831 状态，第三层构建时每状态要比 637 个 move，这就烧掉了 13.4s。

### 修复：新增 `_CLOSING_WORK_LIMIT`

计数 `work += len(moves)`（每个 prev 状态一次），超限即返 `None`。**实测扫描阈值**：

| 阈值 | NP01 成功 | NP01 耗时 | C60 成功 | C60 耗时 |
|---|---|---|---|---|
| 50k | 7/15 | 7.95s | 5/10 | 18.01s |
| **100k** | **8/15** | **6.65s** | **5/10** | **13.21s** |
| 250k | 9/15 | 9.55s | 5/10 | 26.02s |
| 500k | 9/15 | 11.88s | 6/10 | 42.75s |
| 1M | 9/15 | 13.70s | 7/10 | 66.44s |

**100k 是两列时间的同时最小值**，取之。250k 只多救 1 对 NP01，代价是慢 43%。

### 修复：`_CLOSING_NEG_CACHE`（只缓存负结果）

键 `(ids, blank.bid, target, budget)`，其中 `target = tuple(remaining)`。**`produced` 不是搜索输入**（搜索只从 `target` 做减法），所以函数确实是这四个量的纯函数。

- **只缓存负结果**，因为正结果是 round 列表，回放到不同贪心状态会出错；负结果是对 `(blank, remaining, budget)` 的独立断言，可以共享。
- 两个写入点：① 某层 `current` 为空（**已证明**在该轮数内不可达）；② 跑完全部轮数仍未命中（**已证明**超出预算）。
- **work 超限不得缓存**——那是"未知"而非"否"。

## 关键 bug：`search_10s` 的种子与退火共用 deadline

**症状**：`search_10s(60 单, seconds=25)` **必然抛 `SearchTimeout`**，而同样 60 单的分组只需 36s。
`smoke_semi.py` 侥幸没暴露，是因为 30 单（16s 分组）刚好压在 50s 内。

**根因**：`search_10s` 设 `deadline = started + seconds - reserve` 后**同时**喂给 `_seed_group` 和退火循环。
但两者的性质根本不同：
- **种子阶段不可截断**——clause 12 要求每单都有方案，`_seed_group` 必须跑完
- **退火阶段可截断**——邻域搜索随时可停

共享 deadline 的后果：`seconds` 小于分组成本时，`_seed_group` 被截断成**半成品计划**，
紧接着的 `_deadline(deadline)` 复核抛 `SearchTimeout`——把「给的时间不够构造」误报成「实例不可行」。

**修复**（`solver.py`）：
1. `_seed_group(model, group, construct, rng, None, orders, cfg)` —— **传 `None` 表示无时钟**
2. 删除种子后那句 `_deadline(deadline)` 复核
3. 退火循环保持 `_deadline(deadline)`，`SearchTimeout` 由 `except` 捕获 → 正常返回计划
4. 新增 `_expired(deadline)` 软检查助手（`None` 恒为未过期），替换 6 处裸 `time.perf_counter() >= deadline`
   —— 裸比较遇到 `None` 会抛 `TypeError: '>=' not supported between 'float' and 'NoneType'`

**验证**：60 单 `search_10s(seconds=25)` 由「必抛异常」→ **36.66s 返回 30 个方案**。

**同步修改**：`test_solver.py::test_empty_infeasible_and_limits` 原断言 `seconds=1e-12` 抛
`SearchTimeout`，该断言**编码的正是这个 bug**。改为断言「返回合法计划」，
真正的守卫是 `seconds=0` → `ModelError`（`_positive`）。

## 关键 bug：`_solo_scheme` 超产判据用 `<` 而非相等

**症状**：`search_10s` 内部 `validate_plan` 抛
`Demand/overproduction violation for B20270141: 450, allowed [447, 447]`。

**复现**：`NP01:43` 第 120~180 单，`seed` 扫描在 131 命中（120~139 中仅 1 例，
说明它是**时序/seed 相关**而非必现）。

**根因**（`_solo_scheme.try_shape`）：订单 447 件、size 4.9m。

```python
total_k = _ceil(order.pieces / parallel)      # parallel=5 -> ceil(447/5)=90
per, extra = divmod(total_k, n)               # n=3 -> per=30, extra=0
ks = [30, 30, 30]                             # 每轮 30*5=150 件，共 450
if sum(k * parallel for k in ks) < order.pieces:   # 450 < 447 ? 否 -> 通过！
    continue
```

`<` 只挡住**欠产**，挡不住**超产**。而 `max_overproduction_ratio=0` 要求**精确等于**。
注释本就写着「never exceeds the demand」，代码没落实。

**修复**：改为整除判据（也更快，省掉后续 `sum`）：
```python
total_k = _ceil(order.pieces / parallel)
if total_k * parallel != order.pieces:
    continue          # 该 parallel 无法精确落地
```

**教训**：`ceil(pieces/parallel)*parallel == pieces` 仅当 `parallel | pieces`。
这是一条**算术硬约束**，和 `_closing_rounds` 里 946/1156 的整除条件是同一类问题。

## ⚠️ 反转：`_solo_scheme` 的整除判据对本赛题是**错的**（22:15–22:45）

**上文「关键 bug：`_solo_scheme` 超产判据用 `<` 而非相等」把方向改错了。** 那次把
`if total_k * parallel < order.pieces: continue` 改成 `if total_k * parallel != order.pieces: continue`，
即要求 **`parallel` 整除件数**。这条改动在全量求解上直接炸掉：

**症状**：`solve_semi.py` 在 `NP01:43` 的 `@120 / @300` 连续抛
`ModelError: Search found no feasible scheme for B20270288; not a proof of infeasibility`。
`B20270288 = NP01, 43mm, size 6.55m, 23501kg` → **251 件（质数）**，`parallel_limit=46`，
`p ∈ {1}`，而 `p=1` 时 `total_k=251`、6 轮均摊每轮 42 段 → `42*6.55 = 275m > 150m` → 无解。

**根因是规则口径，不是实现细节。** `max_overproduction_ratio=0` 是**从初赛 `prepare_data.py`
继承来的默认值**，`prepare_semi.py` 里对它的注释引用的是 clause 4（轮数），**根本没有为 0 引用任何条款**。
而复赛的三处证据一致指向「超产合法」：

| 证据 | 原文 / 位置 |
|---|---|
| `data/semi/constraints.txt` 第 8 条 | 「每订单冷床分配总重量须**不低于**该订单重量」——**单边下界**，且 12 条里**没有一条禁止超产** |
| `RULES.md` §1 / §12.5 | 「改为**欠产惩罚**（少生产扣分）；**超产不扣分，但超产部分不计入成材率**」 |
| `platform_check.py:215-222` | 代码里已把件数需求当单边下界，只报 `short_delivery` |
| `platform_score.py` | `numerator_capped_by_demand` 已实现「分子按需求封顶」 |

即：`==` 要求的是**比规则更严**的约束，把「浪费不计分」错当成「违规」。

**量化**（新增 `diagnostics/semi_overproduction_probe.py`）：

- 现行 `==` 规则下 **3,304 / 9,999 单（33%）无任何合法方案** → 每单 = clause 12 违规 1 条 = −5 分。
- 这些订单**被迫**超产的幅度极小：3,135 单 ≤0.5%（多数只差 1–3 件）、169 单 ≤2%、**>2% 为零**、
  **物理无解为零**。→ **2% 是让全部订单都能落地的最小 cap**（1% 剩 3 单落空，0.5% 剩 169 单）。

**修复（两处）**：

1. `prepare_semi.py`：`max_overproduction_ratio` 由 `0` → **`0.02`**（含完整证据注释）。
   同步 `data/semi/competition.config.json`。
2. `solver.py::_solo_scheme`：删掉整除判据，改为**解析式枚举**。对固定 `parallel`，
   合法段数是一个**连续区间** `[k_lo, k_hi]`（50/150m 窗口与 60t 上限都是对 `k` 的界），
   于是 `n` 轮下的最少段数 `total_k = max(n*k_lo, ceil(pieces/parallel))`，上限 `n*k_hi` 且受 `caps` 约束，
   区间内每个值都可达。排序键 **`(total_k + n, parallel*total_k)`**：
   `total_k + n` 正是刀数（`sum(ks)+1` 每轮），`parallel*total_k` 是不计分的超产。
   `n` 从小到大扫 → 小 `n` 同时省刀数和省超产。

**验证**：`diagnostics/semi_solo_placement.py` 对全 9,999 单实跑 → **0 失败**；

**顺带修正的三处过时注释**（都写着「超产被禁止」）：`_pack_group` docstring、`_construct` 末轮注释、

## 刀数 / 成材率：全盘量级与一个未决的战略问题（23:00）

从已完成 chunk 直接统计（`knives = 段数 + 1` 每轮，即 `net_shared_trim` 口径）：

| 运行 | 件数 | 刀数 | 刀/件 |
|---|---|---|---|
| `capexp/cap002` | 234,227 | 18,256 | 0.0779 |
| `semi_v2`（前 3 块） | 133,110 | 10,438 | 0.0784 |

**外推全盘 10,242,863 件 → `K ≈ 800,000` 刀。**

⚠️ **战略问题（需与赛题组确认，`RULES.md` §13#3 已列为未答）**：刀数子分是
`0.4 * min(100, 100 * B / K)`，`B` 是**刀数基准**。`RULES.md` §3.1 确认的是**初赛** B = 90000
（由 6 个反馈点反解），**复赛的 B 未公布**，`prepare_semi.py` 里明确写着 “knife baseline for the
semi-final round is unknown; left unset”。

- 若复赛 B 仍是 **90000**：`100*90000/800000 = 11.25` → 刀数项只剩 **4.5 / 40 分**，满分上限约 63.5。
- 若 B **随数据集规模同比放大**（初赛 ~1000 单 / K≈11.9 万 → 复赛 9999 单 / B≈90 万）：
  `100*900000/800000 > 100` → 封顶 → **满 40 分**，总分约 99。

**判断依据**：初赛三个官方反馈点是 `(K=113683, 成材率 86.63)` / `(92913, 92.51)` / `(119268, 96.71)`
（`diagnostics/yield_semantics.py`）——**刀数最高、成材率也最高的那个提交**才是最好的一档，
说明初赛里成材率的边际价值高于刀数。若 B=90000 作用于复赛，`K` 会在 70–90 万之间几乎不变，
刀数项对所有人都是 ~11 分、失去区分度，赛题组不太可能这样设计 → **B 大概率是分赛段标定的**。

**对求解器的含义（重要）**：`solver._key` 的刀数项是 `40 * min(1.0, baseline_knives / knives)`，
而它作用在**单个 scheme** 的刀数上（一个 2 单对只有 ~10–30 刀），`B/K` 远大于 1 → **恒为满分、是常数**。
所以 `search_10s` 实际优化的是 **成材率 + 覆盖率**，不是刀数。这是合理的默认：
- 按每单刀数看，复赛（80 刀/单）其实**优于**初赛（119 刀/单），说明当前解并没有为了省刀而牺牲成材率。
- 提高 `parallel` 可以减少刀数（段数变少）但会**降低成材率**（2m 切损分摊变差），
  这是一个真实取舍；在 B 未确认前**不应单方面压刀数**。

**结论：暂时保持「最大化成材率」的默认行为，把 B 的问题留给赛题组/用户决策。**
`_solo_scheme` 的排序键取 `(total_k + n, parallel*total_k)`（刀数优先），在 `ratio=0.02` 下
实测成材率并不劣于「大 t」方案（大 t 会放大超产比 `o/(p*t)`），且 solo 只覆盖 ~1% 订单，影响可忽略。

## 刀数与成材率的结构关系（22:25，重要）

### 两个精确恒等式（从 `make_round` 直接推出）

对一轮冷床，记 `L = Σ_i k_i s_i`（该轮净长，m）、`p` = parallel（并排棒数）、`mu` = 线密度。
`make_round` 写的是 `raw = (L + 2)·p·mu`、`finished = L·p·mu`，于是

1. **成材率只取决于轮净长，与 `parallel` 无关**：
   `Y_round = L / (L + 2)`。`p` 在分子分母中**完全约掉**。
   整个方案 `Y = Λ / (Λ + 2·Σ_r p_r)`，其中 `Λ = Σ_r p_r L_r = Σ_orders pieces·size`（固定）。
   → **要提成材率，唯一办法是把轮做长**（轮长的上限是辊道 150m 与承重 `p(L+2)mu ≤ 60000`）。
2. **刀数** `K = Σ_r (Σ_i k_i + 1) = Σ_r L_r/s̄ + R`。
   而 `L_r = Λ_r/p_r`，所以 **`p` 越大 → `Σ L_r` 越小 → 刀数越少**。

**两者冲突**：承重式 `p(L+2)mu ≤ 60000` 让 `p` 与 `L` 互为代价——
`p` 大则 `L` 必须小（成材率降），`L` 大则 `p` 必须小（刀数升）。

### 用真实方案验证（`runs/capexp/cap002`，1660 轮 / 332,888 件）

| 指标 | 实测 |
|---|---|
| 刀/件 | **0.0781** |
| 实现成材率（净长加权） | **0.9708** |
| 平均轮净长 | **79.6 m**（中位 58.3） |
| 平均 parallel | **16.2**（中位 14，max 44） |
| 每轮承重利用率 | `81.6×16.2×15.68 = 20,730 kg`，**仅为 60t 上限的 35%** |

**每轮只用了 35% 的承重上限** → 在同样的轮长下 `p` 可以提到 ~45，那样轮数减少 ~2.8 倍、
`Σ L_r` 同步减少 → **同样成材率下刀数可降约 2.8 倍**。这是当前解最明显的浪费。

### 为什么求解器没做到

`_key` 的刀数项是 `40 * min(1.0, baseline_knives / knives)`，`baseline_knives=90000`：

- 在**单个 scheme** 上（一对 ~10–30 刀）：`90000/30 = 3000` → `min` 恒取 1 → **常数**；
- 在**整个 chunk** 上（`search_10s:1884` 用的是 `_totals(current.values())`，60 单 ≈ 4,800 刀）：
  `90000/4800 = 18.75` → 仍恒取 1 → **还是常数**。

所以 `search_10s` 实际只在优化 `30*成材率 + 20*覆盖率`，**刀数完全不被搜索感知**，
`p` 落在哪个值纯属构造顺序的副产品。这也解释了为什么解会停在「中低 parallel」上。

### 待决策（依赖 `B`）

若复赛 `B` 仍是 90000：`100*90000/800000 = 11.25` → 刀数项只 4.5/40，而把 `p` 推到承重上限
可降到 `K ≈ 290,000` → 该项 ~12.4/40，**净赚约 8 分**，成材率几乎不变（同轮长）。
若 `B` 是分赛段标定的（初赛 ~1000 单 K≈11.9 万 → 复赛 9999 单 `B`≈90 万）：该项本来就封顶，
压刀数无收益。

**这是「无风险下限」**：在**不改变轮长**的前提下提高 `p`，成材率不变、刀数下降——
无论 `B` 取何值都不会变差。**应优先做这件事**（改 `_construct` 的 parallel 选取偏好，
或给 `_key` 一个不被饱和的刀数项）。改轮长（`L`）则是真正的取舍，需先定 `B`。
