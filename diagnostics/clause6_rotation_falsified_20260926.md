## 1. 证伪实验

2026-09-26 15:45 提交 `submission_semi_merged_v4`（已过键旋转、本地读法 B = 0）。
平台在 15:45:18 评估，回读的附件 SHA-256 与提交的 ZIP 一致（`attachmentMatches: true`）：

```
不可行，总分=0；违规次数：7342条，累计扣分36710分；
跨轮接续不连续(7342条)：方案0批0、方案0批1、方案0批2、方案0批3、方案0批4、
方案1批0、方案1批1、方案1批2、方案1批3、方案2批0、方案2批1、方案2批2…等7342处
```

**旋转把本地计数从 7344 打到 0，平台却仍然报 7342 —— 几乎没动。**
旋转改的是 `length_scheme` 里字典的**键插入顺序**；平台的计数对这个顺序不敏感。
**`rotate_scheme_rounds` 是一步空操作，从来没有修复过任何东西。**

## 2. 上一轮为什么判错

`clause6_confirmation` 把「前 12 个定位逐位一致」当成了强证据。实际上：

- 官方定位是 **(方案, 批)** 对，**任何按轮边界计数的判据**都会产出这种串。
  它只能排除「按订单计」的读法 D，**不能区分 B 与其它边界判据**。
- 更关键：在 `merged_v2` 上，三种**不同的键顺序语义**给出同一个 7030：

| 语义 | v2（原始） | v4（已旋转） |
|---|---:|---:|
| 字典插入序（读法 B） | 7030 | **0** ← 与平台 7342 矛盾 |
| 排序序（sorted） | 7030 | 7344 |
| 方案 `orders` 列表序 | 7030 | 7344 |

v2 上三者重合，**样本无区分度**——正是 `clause6_OPEN_RISK` 警告过的那个陷阱
（「7559 样本无区分度」）。区别是这次我踩了它。

## 3. 修正后的判据

平台用的是**规范顺序**（按方案自己声明的 `orders` 列表，或等价地按排序），
不是 JSON 里的键插入顺序。最接近的判据：

> 相邻两轮有共同订单，且 **在方案 `orders` 列表序下**左轮最后一个订单 ≠ 右轮第一个订单

| | 预测 | 官方 |
|---|---:|---:|
| `merged_v2`（原始） | 7030 | 7030 ✅ |
| `merged_v4`（已提交） | 7344 | 7342 ❌ 差 2 |

残差 2 条尚未定位（`intersection >= 2` 之类的小条件能把 v4 修到 7342，但会把 v2 打到 7028）。
**需要更多官方锚点才能把判据钉死。** 但方向已经确定：**旋转无效，必须做结构修复。**

## 5. 结构修复要满足什么

现在每个方案的**每一轮都带同一批共享冷床订单**。在规范序判据下，要让每个
「有交集」的交界满足 `last(左) == first(右)`，必须让共享订单在左轮排在
`orders` 列表**最末**、在右轮排**最前**——同一批订单不可能同时满足三轮以上。
所以这个方案族**在结构上就不可能合规**，必须改轮次/订单的分配结构，
而不是改键顺序。
