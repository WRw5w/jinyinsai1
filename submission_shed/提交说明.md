# 削产包 —— 「申报钢更少 / 刀数更少」两个猜测的对冲包

## 一句话

我们原来的方案**多产了 105,054 件（+2.06%）没人要的成品**，折合 **5,516,308 kg** 成品质量。
这部分剩余对总分**完全无影响**（`成材率 = A / raw`，产多少报多少，比值不变），
所以搜索链路从来没有理由去避免它——它也确实没避免。

但它恰好膨胀了两个「名次猜测」所排的量：

- **申报钢** `raw = Σ blank_count × BW`（逐坯型 `ceil(A_bt/BW_bt)` 保险随 A_bt 走，所以 raw 跟着 A 走）
- **刀数** `K = Σ max(2, k)`（K 跟随 `Σk`，而 `Σk = 产出 / 并行根数`）

本包把剩余削掉，并重新申报最小坯数。

## 数值

| 项 | 基线（L3 原包） | 本包 | 变化 |
|---|---|---|---|
| 成品总质量 A | 253,897,757.334 kg | **250,805,976.317 kg** | −3,091,781 kg（−1.218%） |
| 申报钢 raw | 253,905,353.0 kg | **250,817,940.5 kg** | **−3,087,413 kg（−1.216%）** |
| 申报坯数 | 8353 / 28171 | 8228 / 27865 | −125 / −306 |
| 刀数 K | 90000 | **89626** | −374（−0.42%） |
| 覆盖 C | 100% | 100% | 不变 |
| 残差 raw − A | 0.000 | 103.905 kg | 成材率 99.999958573% |

逐坯型保险**完好**：`declared = ceil(A_bt/BW_bt)` 精确相等（8228 / 27865）。

## 削产动作（只会**减少**物料，所以物理约束自动安全）

| 动作 | 效果 | 约束 |
|---|---|---|
| `k → k−1`（不低于 1） | 少 `count` 件；`k ≥ 3` 时省 1 刀 | 该订单剩余量 ≥ 需求；net−size+2 ≥ 50 m |
| `count → count−1` | 每个段少 `k` 件；**不省刀** | 该轮所有订单都还有余量 |

`k` 动作只动一个订单，所以按订单解**有界背包**（精确不越需求）；
`count` 动作按整轮收益 `K_r = Σk` 降序贪心，两者交替迭代到不动点。

实测：**555 次 k 削减 + 2148 级 count 削减**，剩余从 105,054 件降到 45,623 件。

## 为什么没削干净：刀数键其实已经挖尽了

`k` 削减一次吃掉 `count ≈ 55` 件的余量，而全库余量只有 105,054 件，
所以可做的 k 削减上限约 `105054 / 55 ≈ 1910` 次；实际受**分布**限制只做到 555 次
（多数订单余量只有 ~21 件，凑不出一次 55 件的削减）。

更关键的是 `count`（并行根数）**已经顶死在床宽上限**：

```
p / min(床宽上限 2000/dia, 床重上限) 均值 0.966
p ≥ 98% 上限的轮数：3452 / 5346
床宽约束是紧的轮数：5127 / 5346
```

所以真实刀数下界是 `Σ need_o / floor(2000/dia_o)` ≈ **86,237**（−4.2%），
而我们的方案（90000）已经拿到其中 90% 以上的结构效率；本包再拿 −0.42%。
想再往下只能整体重构（每订单压成一段），收益上限也只有 4.2%。

**结论**：「刀数最少」和「申报钢最少」这两个键在本方案上**收敛到同一个最优点**，
所以只出一个包。单独的刀数模式（`runs/fill/shed_knives.json`，刀数 89472、
申报钢 252,717,469.5）在两个键上都劣于本包，仅供参考。
