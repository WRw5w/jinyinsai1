## 0. 摘要

> **本版是 clause 6 合规化后的重交版，取代上一版。** 上一版被平台判定为
> **不可行、总分 = 0**，`跨轮接续不连续` **7,559 条**（累计扣分 37,795）。根因、判据反推
> 与修法见 §5.4：旧定形器把每个订单放进**每一轮**，于是方案内任意相邻两轮的订单集合
> **完全相同**，逐条命中判据。官方给出的定位串（`方案0批0..批4、方案1批0/1/2/4、
> 方案2批0..批2`，其中含「方案 1 恰好缺批 3」这一不可伪造的指纹）已被
> `diagnostics/semi_continuity_audit.py` **逐字复现**。新定形器 `continuity_shaper.py`
> 改为枚举 `(m, R)` 的**全部合法区间结构**（同一订单轮次连续、每轮非空、相邻两轮集合
> 不得相同）；本版在该判据下为 **0 条**。

本报告给出复赛（9,999 个有效订单）的完整求解方法与验证结果。求解器把问题分解为
「**按钢种/规格分组 → 逐方案连续性定形 → 容量/净长感知装桶 → 双目标选点**」四步，全部只用 Python
标准库，整卷构建 **431 秒（16 进程并行）**（对比之下，原随机邻域搜索约需 **46 秒 CPU / 60 单**，
外推全量要数小时，且会输出刀数高一倍的方案）。

在自建的**三层验证闸门**（独立物理校验器 `platform_check`、求解器自带
`validate_plan`、评分模型 `platform_score.evaluate`）下，最终方案：

| 指标 | 结果 |
|---|---|
| 有效订单覆盖 | **9,999 / 9,999**（源数据 10,000 单中 1 单为异常数据） |
| 物理/结构校验 | **通过**（`platform_check` 19 类错误全为零） |
| 规则违规数 | **0**（`violation_count = 0`：无欠产、无跳轮、无超轮数） |
| **冷床接续（clause 6）** | **0 条**（相邻两轮集合完全相同 = 0；订单跳轮 = 0） |
| 刀数 | **176,563**（`nearest` 读法为 **185,577**）⚠️ 取整口径未决，见 §6.6 |
| 方案数 / 冷床轮数 | **1,855** / **9,914** |
| 成材率（评分分子，超产不计入） | **89.80%** |
| 组合覆盖率 | **100.00%**（9,999 / 9,999 单参与过多订单轮次） |
| 本地模型总分 | **93.187**（B=160,000）/ **77.329**（B=90,000）⚠️ 绝对值为区间，见 §6.7 |

> ⚠️ **合规是有代价的，这里把代价写清楚。** 以同一超产允量 `r = 0.10` 逐项对比：合规化使
> 刀数 175,952 → 184,363（+4.8%）、成材率 91.81% → 90.30%，折算 **−2.11 分**（B=160k）。
> 旧包刀数更低，恰恰是因为它把每单塞进每一轮、做出了**共享率最高但违规**的轮。
> 在合规族内重新扫描 `r` 之后，选 `r = 0.25` 换回 **+1.38 分**（§6.2，代价为成材率
> −0.50 个百分点）。净效果相对旧包为 **−0.73 分**，但旧包的实际得分是 **0**。

> ⚠️ **刀数取整口径是最大的未决事项**（§6.6）：同一份方案在 `int(L//size)` 与 `nearest`
> 两种读法下相差 **9,014 刀（5.1%）**，B=90k 下值 **0.99 分**、B=160k 下值 **1.76 分**、
> B=180k 下值 **1.20 分**（后者不比 160k 高，因为刀项此时已封顶）；
> 上表刀数用 `int(L//size)` 口径，区间为 **176,563 ~ 185,577**。

> ⚠️ **基准刀数 B 与 λ 的联动**（§6.7 是对前稿的更正）：`B = 160000` 只见于群答疑归档
> （`evidence/rules/BASELINE_160000_SOURCE.md`），`RULES.md` 所记的 90,000 是**初赛**值。
> 本版 λ 由 12 点扫描在 B=160,000 下选出 **λ = 4800**，且是**内部**最优而非网格边缘
> （相邻点为 93.183 / 93.176 / 93.167）；λ 的最优点随 B 移动，见 §6.7。

本轮的三个关键结论（均带可复现证据）：

1. **clause 6 把「轮」从一个自由容器变成区间结构的投影**。这是复赛与初赛最大的结构差异，
   也是上一版被直接判 0 分的唯一原因——求解器必须先保证**存在**这样的结构，再谈优化；
2. **合规化会把最优点推向更大的超产允量**。约束收紧「一单占几轮」的自由度之后，
   刀数的主导量从「并列支数取小」变成「行数」，而放宽 `r` 才能让定形器把行并起来：
   §6.2 的曲线随 `r` **单调上升**（243,721 → 176,563 刀），与前稿在旧定形族上
   「`r ≥ 0.10` 后饱和」的结论**方向相反**；
3. **成材率的主要损耗仍是「整根钢坯向上取整」**，而不是切损（§6.5）。

## 2. 评分模型口径

复赛评分沿用 PDF 第九页的权重表：

```
总分 = 0.40 × 刀数子分 + 0.30 × 成材率子分 + 0.20 × 覆盖率子分 + 0.10 × 时间子分
       − 5 × 违规次数
```

### 2.1 刀数子分

本轮计刀口径被赛题组**修正**过（`RULES.md` 第 23 行）：初赛「给每个订单都加头尾」，
复赛改为「**连接处算一刀，每轮冷床只有一组切头切尾**」。落到实现即：

```
每轮刀数 = Σ_订单 int(length // size) + 1
```

其中 `length` 是该订单在本轮申报的净长度（定尺整数倍），`size` 是定尺长度。
注意这里是**浮点整除**语义：导出时写 `round(k * size, 9)`，在某些 `(k, size)` 组合上
`round(k*size, 9) // size` 会比 `k` 小 1（实测占 39.8% 的组合），我们严格照抄这一
浮点行为，不做「修正」。

刀数子分 = `100 × B / 刀数`，其中**基准刀数 B 未获复赛官方确认**（初赛为 90000）。

### 2.2 成材率子分

```
成材率 = Σ_订单 min(该订单产出重量, 该订单需求重量) / Σ_轮 申报钢坯重量
```

**分子**是成品重量，复赛**剔除超产部分**（`RULES.md` 第 19、43 行；
超产部分「不计入成材率」）；成品重量按**直径截断到整数毫米**再算圆截面
（该口径由三份初赛官方反馈复现得到）。**分母**是各轮申报钢坯重量之和，
两端各 1 m 的固定切损计入承重校验、也进分母。

### 2.3 覆盖率子分

初赛「同一批内不同轮次切过即可」在复赛被**收紧**：必须**在同一轮次共同上冷床**
才能算有效组合（`RULES.md` 第 21 行、答疑 09-14 15:45）。
因此覆盖率 = 参与过「多订单轮次」的订单数 / 有效订单数。

### 2.4 未决口径

- **刀数基准 B**：复赛值为 **160000**，出处是群答疑（09-21 15:46「★ 复赛基准刀数
  = 160000」），档案见仓库 `evidence/rules/BASELINE_160000_SOURCE.md` 与
  `evidence/rules/RULES_SOURCES.md`；⚠️ 该出处是**群答疑记录**而非 PDF / `constraints.txt`
  明文（两者均未给基准值），`RULES.md` 记的 90000 是**初赛**值。本报告同时在
  B = 90000、160000 与 180000（按订单规模线性外推）三种假设下给出结论，见 §6.3；
  ⚠️ **B 不只影响绝对分数，
  还影响 λ 的选点**——刀数子分随 B 线性放大"每刀值多少分"，而 B ≥ 总刀数后刀项封顶、
  目标退回纯成材率，因此最优点先右移再左移。§6.7 在**两代定形族**上各给一张表：
  **交付族**（`continuity_shaper` + `r = 0.25`，§6.7.1）三档 B 下的族内最优 λ 是
  2400 / **4800（= 交付点）** / 1200（floor 口径），最坏遗憾 0.257 分；
  旧族（`round_shaper`，§6.7.2，历史对照）是 2400 / 4800 / 1200，最大差距 0.2134 分；
- **时间子分**：同一页 PDF 上存在**两种互相冲突的表述**——正文写 40% / 30% / 20% / 10%
  （时间独立占 10%），紧接着的**公式**却写 `40 × 基准刀数/总刀数 + 40 × 成材率
  + 20 × 覆盖率`，即 40/40/20、**根本没有时间项**（`README.md` 第 165 行记录了这处矛盾）；
  群答疑又称「时间并入成材率子项」（`RULES.md` 第 25、47 行）。本报告以 PDF 正文版
  （独立 10%）为主口径实现，并在 §6.3 用 (0.4, 0.4, 0.2, 0) 对「无时间项」版做了对照——
  后者在数值上同时等价于「时间并入成材率」的说法，结论不变；
- **时间子分若被实测**：本模型按满分 100 计（`Rules.time_subscore = 100.0`）。
  我们没有官方的时间标尺，只能给出可比的绝对量级——交付方案从原始数据到成品提交包
  的**实测墙钟约 75 秒**（§4.5），对比原分块搜索的近 2 小时，即使官方按运行时间打分，
  也应是接近满分的量级。

## 3. 三个关键发现

### 3.1 复赛允许超产（决定路线的一条）

约束 7、8 都是**单边下界**（「**不低于**」），12 条中没有一条禁止超产。`RULES.md`
第 18、19 行进一步明确：

> 复赛：**改为欠产惩罚**（少生产扣分）；**超产不扣分，但超产部分不计入成材率**。

四条独立证据：

1. `constraints.txt` 第 7、8 条为「不低于」的单边下界；
2. `RULES.md` 第 18 行「超产不扣分」、第 19 行「成材率分子不包含超产成品」；
3. 独立校验器 `platform_check.py` 的 **19 类 error kind 中没有超产类**，
   且第 215–220 行注释明确写道：「超产不是 checker 的违规，
   超产扣分住在 `platform_score.Rules.numerator_capped_by_demand`」；
4. `platform_score.evaluate` 对分子逐单封顶（`min(产出, 需求)`）。

**这一条的实际含义**：超产**只通过分母惩罚自己**（多产 → 多申报钢坯 → 成材率下降），
不存在额外罚分。因此「允许少量超产」是一个合法的**求解设置**，其代价可以在评分模型内
被精确计价 —— 这为 §4.3 的「重定形」提供了关键自由度。

### 3.2 刀数在整卷尺度远未触顶 —— 它才是主战场

早期结论认为「`40 × min(1, 90000/刀数)` 恒被饱和，所以刀数对搜索不可见」。
该结论**只在单个分块内成立**：分块只有 60 单，刀数约 2,700，远小于 90000。
但评分是在**整卷**上计算的：

```
整卷刀数 K ≈ 450,000   （由 60 单分块实测 2,546 刀外推）
刀数子分 = 100 × 90000 / 450000 ≈ 20   （满分 100）
```

即刀数一侧损失 `0.4 × (100 − 20) = 32 分`，而成材率一侧（0.82 对 1.0）
只损失 `0.3 × 18 = 5.4 分`。**刀数是量级更大的杠杆。**

这个外推在 §5.3 的单块实验里被证实，并在全卷求解完成后闭环：重定形把单块刀数
从 2,546 降到 1,019（17.0 刀/单），按比例外推 9,999 单得 **170,000 刀**，
与全卷实测 **176,563 刀** 相差 3.9%（§6.1）。也就是说，「并列支数取小」这**一个**
系统性选择就值约 **25 万刀**，折合 **12 分**（B=90,000）到 **23 分**（B=180,000）。

### 3.3 成材率的主要损耗是「整根钢坯向上取整」，不是切损

每轮的钢坯约束是

```
blank_count × usable ≥ total × parallel,   usable = blank.weight / μ
⟹ blank_count = ⌈ total × parallel / usable ⌉
```

由于 `usable` 很大（`BT5` @ φ43 → 615.9 m/根），而一轮实际只需约 0.9 根，
向上取整到 1 根就凭空多申报一整根钢坯。实测原方案：

```
申报钢坯总量 / 物理需要总量 = 3,249,574 / 2,753,523 = 1.1802
```

**18.0% 的申报钢坯是纯粹的取整余量**，远大于 2 m/轮 的共享切损（约 2.5%）。
这就是成材率被压在 0.823 的直接原因。

重定形（§4.3）之后，交付方案的申报钢坯总量降到 **557,847 t**，成材率随之从 0.823
升到 **0.898**；剩下的 10.2% 差额就是「2 m/轮 共享切损 + 残余的整根取整余量 + 2.6% 超产」。
换算到分数：成材率一侧的损失从 `0.3 × 17.7 ≈ 5.3 分` 压到 `0.3 × 10.2 ≈ 3.1 分`
（四项精确分解见 §6.5）。

## 4. 算法

### 4.1 总体结构

```
9,999 单
  │  ① 按 (钢种, 规格) 分组                            → 36 组
  │  ② 组内装桶：质量 + 净长双口径、按利用率均衡         → 1,855 个桶
  │  ③ 逐桶枚举 (m, R) 的**全部合法区间结构**（clause 6） → 帕累托候选集
  │  ④ 用 Lagrange 乘子 λ 在「申报钢坯 × 刀数」双目标上选点
  ▼
result.json（clause 6 审计 / platform_check / validate_plan / evaluate 四道闸门通过）
```

第 ③ 步是本版新增的核心（§5.4）：上一版把「每单进每一轮」，在 clause 6 下**必然全违规**；
本版改为枚举区间结构，即把「存在合法解」变成**前置条件**，再谈优化。

### 4.2 装桶：为什么不再是「两单配对」

原搜索 `search_10s` 用约 46 秒 CPU（每 60 单）同时决定**配对**与**每轮形状**。
上一版据此把配对退化成「组内两单配对」，理由是覆盖率只要求「同一轮次共同上冷床」。
**clause 6 之后这条理由失效**：轮次被锁成区间结构后，一个桶里放几单、放哪几单会直接
改变可行的 `(m, R)` 与行数，从而改变刀数。于是第 ② 步改成**质量 + 净长双口径装桶**：

* **两条上限必须同时把关。** 桶的质量上限是 `Σ ≤ 床重 × R`，但 `scheme_candidates`
  真正卡的是**净长**：`spread = Σ ⌈P_i / p⌉ × 定尺 ≤ R × (bed_len − trim)`。
  只按质量装会造出「质量达标、净长却超」的桶，`scheme_candidates` 直接返回空
  —— 这正是大组上大量桶定形失败（`dead` 桶）的根源。两条口径分别由 `bin_capacity`
  与 `bin_row_capacity` 给出，后者取 `cap_len = min(bed_len, 床重/(plimit·μ))`
  这一**最保守**值（`plimit` 为床宽允许的最大并列数）；
* **选择准则是利用率，不是剩余容量。** 桶容量随单数 `m` 阶梯跳变（`m=3` 的桶容量只有
  `m=4` 的 83%），按「剩余绝对容量最大」会先把大桶灌到 98%~100%、把定形逼到无解，
  而小桶还饿着；按 `max(利用率_质量, 利用率_净长)` 最小者投放（`cap_aware_bins`），
  全部桶才停在 `total / Σcap` 附近，留出可分配余量；
* **桶数 `G` 是搜索变量**：装不下就换 `G` 重试（`build_groups`，目标利用率 0.93），
  并用 `lpt_bins` 作对照、用 `balance_bins` 做桶间订单交换以压低最大桶利用率
  （邻域过大时直接退回未均衡结果——均衡只是锦上添花，可行性由前两条负责）。

单订单桶是允许的（仍满足 clause 6，只是拿不到覆盖率）。全卷平均 **5.4 单/桶**
（最大组 `NP01:43` 的 3,532 单装成 638 个桶），9,999 单**全部进桶**，覆盖率 100%。

### 4.3 逐方案重定形：把「怎么分轮」和「交多少件」解耦

对一个方案内的订单集合，设订单 `i` 的需求件数为 `P_i`，允许上限
`C_i = P_i + ⌊P_i × r⌋`（`r` 为超产允量）。**关键简化**：

> 若 `n` 轮使用**同一个** `parallel = p`，则订单 `i` 得到的件数是 `K_i × p`，
> 其中 `K_i` 是订单 `i` 在单根棒材上的**总段数**。
> **件数与「怎么把这 `K_i` 段摊到 `n` 轮」完全无关。**

由此得到两个解耦的决策：

**决策一：`K_i` 取最小合法值。** 需求窗口 `[P_i, C_i]` 逐单独立，所以

```
K_i = ⌈ P_i / p ⌉        且要求   K_i × p ≤ C_i
```

就是该 `p` 下刀数最小的合法段数（段数越少刀越少）。

**决策二：`n` 取最小可行值。** 因为刀数 = `Σ_i K_i + n`，而件数与 `n` 无关，
`n` 只需保证**每一轮都落在床的合法区间内**。设

```
cap_len = min(150, 60000 / (p × μ))        # 床长上限与承重上限的联合
S = Σ_i K_i × size_i                       # 单根棒材上的总成品长度
```

把 `S` 摊到 `n` 轮，则每轮长度为 `2 + S/n`，必须落在 `[50, cap_len]`，于是

```
n × (50 − 2) ≤ S ≤ n × (cap_len − 2)
```

枚举 `n ∈ [n_lo, n_hi]`，对每个 `n` 用一次贪心均衡分配 + 越界回填把 `Σ_i K_i`
摊到各轮（`parts[i][r] = K_i // n + (1 if r < K_i % n else 0)`，再按最重/最轻轮
互相搬运，200 步内不收敛就丢弃该 `n`），最后按 `(刀数, 申报钢坯)` 做帕累托裁剪。
由于刀数与申报钢坯都随 `n` 单调不减，边界上实际只留下最小的几个 `n`。

**clause 6 修正了这一段的枚举对象。** 上一版枚举的是「把 `Σ_i K_i` 段**均摊**到 `n` 轮」，
隐含「每单进每一轮」——在 clause 6 下必然全违规（§5.4）。本版把枚举对象换成
**每单的连续轮次区间**：先枚举 `(m, R)` 的**全部**合法区间结构，再对每个结构求
`parts[i][r]` 的可行分配（受限轮优先构造 + 局部搜索 + 精确 DFS），并且只作**必要**
剪枝（`_round_bounds` 的 7 条必要条件，全部以上界形式使用，否则会静默误杀可行解）。
帕累托裁剪的依据不变（刀数、申报钢坯），只是候选集从「1 个结构的几个 `n`」
变成「若干结构的帕累托前沿」。

**这一条是原方案的主要缺口。** 原搜索对同一个「交付件数向量」只保留**最小**的
`parallel`（`_enumerate_round_shapes` 中 `if old is not None and parallel >= old[0]: return False`，
`parallel` 循环升序 → 留下第一个即最小者）。但复赛每轮刀数是 `Σ段数 + 1`，
而该轮段数为 `Σ(delta_i / parallel)`，**同一个交付量下 `parallel` 越大刀越少**。
保留最小值正好把刀数最大化了。

### 4.4 双目标选点：为什么成材率只需最小化申报钢坯

因为所有合法候选都交付 `≥ P_i` 件，按 §2.2 的封顶口径，**计入分子的重量恒为
`Σ_i P_i × size_i × μ_int`，是一个常数**。于是

```
成材率 = 常数 / Σ_方案 申报钢坯
```

即：**最大化成材率 ⟺ 最小化申报钢坯总量**，刀数则要最小化 `Σ n`。整卷权衡因此
退化为一个干净的双目标问题 `(Σ刀数, Σ申报钢坯)`。实现用 Lagrange 乘子扫描：

```
每个方案取   argmin( 申报钢坯 + λ × 刀数 )
```

`λ` 的物理含义是「1 刀值多少公斤钢坯」。对全卷扫描 λ 并**用真实评分器
`platform_score.evaluate` 实测每个 λ 的总分**，取最高者；由于候选集只算一次、
可被所有 λ 复用，一次 **12 点**扫描只多花几秒（§6.2 说明为何本版把网格从 9 点扩到 12 点）。

### 5.2 三层验证闸门

每个候选方案都必须通过**三层相互独立**的检查，任何一层不过就不采用：

1. **`platform_check.check`** —— 从原始 GBK CSV 与提交 JSON 独立重算：
   整数倍长度、含余量的床长/承重、床宽、交付数量、钢坯物料、条款 7/8 下界、
   连续性、覆盖率。本轮结果：**`passed = True`，19 类错误全为零**；
2. **`solver.validate_plan`** —— 用与 `make_round` **不同的独立实现**重算约束与成本
   （`blank_rule='per_round'`），并检查 `pieces ≤ produced ≤ caps`、
   订单质量下界、跨方案唯一性、连续性。本轮结果：**通过，9,914 轮，覆盖率 1.0000**
   （其对刀数的朴素计数为 185,577，与平台计费口径 176,563 的差额即 §6.6 的取整口径问题）；
3. **`platform_score.evaluate`** —— 评分模型。本轮结果：**`violation_count = 0`**
   （含 clause 6 相邻轮集合、订单跳轮两项均为 0）；本地总分 **93.187**（B=160,000）。

第四道是**数据侧的独立审计**（`diagnostics/semi_continuity_audit.py`）。它不读求解器代码，
只从题面与两条官方反馈把 clause 6 的判据反推出来（§5.4），并在**同一份旧交付包上复现出
官方的 7,559 条**、在**本包上给出 0 条**。这一道无法由「求解器自查」替代——上一版正是
自己判自己通过、被平台判 0 分的。

此外 `build_submission.py` 在打包后会**重新打开 ZIP 内的实际字节**再跑一遍
（1)(2)，并比对 SHA-256，确保「校验的对象」就是「提交的对象」。

### 5.4 本轮的根因与修法：clause 6「跨轮接续不连续」

**症状。** 平台对上一版回复：`不可行，总分=0；违规次数：7559 条，累计扣分 37795 分`，
全部归入 `跨轮接续不连续`，并给出定位串 `方案0批0、方案0批1、…、方案1批0、方案1批1、
方案1批2、方案1批4、方案2批0、…`。

**判据反推。** 定位单位是 **(方案, 批)**，不是订单——官方串里出现的全是 `方案a批j` 对。
在旧交付包上（`round_shaper` 把方案内**每个订单放进每一轮**，故同一方案内所有轮
订单集合完全相同），两个候选判据给出同一个数 **7559**：

| 判据 | 旧包上的计数 |
|---|---:|
| B 相邻两轮订单集合**有交集** | 7,559 |
| C 相邻两轮订单集合**完全相同** | 7,559 |

必须另找判别证据，而证据指向 **C**：

* 官方题面 PDF 的**输出示例本身**在相邻两轮共享订单（方案 2 第 1 轮含 `A20260104`，
  第 2 轮仍含 `A20260104`）。若「有交集」即违规，官方示例自己就不合法 → B 不成立；
* 该示例恰好是 C 合规的最小演示：集合由 `{104,105}` 变为 `{104}`（**不同**），
  且 `A20260104` 的出现轮次**连续**。它还顺带证明**单订单轮合法**（第 2 轮只有 1 单）；
* 排序后旧包的前 12 项 = `方案0批0..批4、方案1批0/1/2/4、方案2批0..批2`，与官方串
  **逐字一致**——含「**方案 1 恰好缺批 3**」这一不可伪造的指纹。批 3/批 4 之间正是
  `merge_compatible` 的拼接缝，缝两侧来自不同源方案、订单集合不同，故该边界不计违规。
  这个指纹同时把「批 = 轮边界」钉死，也排除了「按订单计」的读法（那会给出
  `Σ m_s(R_s−1)`，比 7,559 大一个量级）。

**结论：clause 6 是两条规则**——① 方案内**相邻两轮的订单集合不得完全相同**；
② 同一订单的出现轮次必须**连续**（不得跳轮）。本实现两条都查。

**修法。** 旧定形器 `round_shaper` 的实现（每单进每一轮）在判据 C 下**必然全违规**，
它是上一版被判 0 分的**根本原因**，且与刀数、成材率无关——方案再优也无效。
新定形器 `continuity_shaper.py` 改为：先枚举 `(m, R)` 的**全部合法区间结构**
（每单一段连续轮次、每轮非空、相邻两轮集合不同），再对每个结构做「受限轮优先构造 +
局部搜索 + 精确 DFS」的段数分配，返回帕累托候选。工程上有三处关键：

1. **`structures()` 的完备性**。`(m=3, R=5)` 有 **10 种**合法区间结构，而原来的
   单调窗口族只给出 1 种——缺的正是让紧箱可行的那些非窗口结构；
2. **必要的剪枝，且必须是「必要条件」**。`_round_bounds()` 加了 7 条必要条件
   （轮容量上下界、轮间耦合、窄窗 bit-set、单订单上界…）。**每条都只作上界使用**：
   早期误写成下界会误杀可行解，属静默错误。已用随机暴力对拍验证：
   **3,967 次试验 / 1,826 个可行实例 / 0 处不一致**；
3. **性能**。`exact_parts` 的 DFS 曾是 87% 的耗时（77 次调用 × 0.46 s）。修法是把
   装坯型的循环**提到**结构枚举之外（`distribute` 与坯型无关，调用次数 2,076 → 418）、
   给 DFS 加预算、并按 key 多进程并行。整卷构建 **431 秒 / 16 进程**。

**验证。** `diagnostics/semi_continuity_audit.py` 在**旧包上复现 7,559 条**、
在**本包上给出 0 条**（C = 0、跳轮 = 0）。这条审计是数据侧的，不依赖求解器的自查——
上一版正是自己判自己通过、被平台判 0 分的。

**代价。** 合规不是免费的：以同一 `r = 0.10` 比较，刀数 175,952 → 184,363（+4.8%）、
成材率 91.81% → 90.30%。旧包刀数更低，是因为它把每单塞进每一轮、做出了共享率最高
但**违规**的轮。合规族内重扫 `r` 到 0.25 后追回 +1.38 分（§6.2）。

## 6. 结果

### 6.1 全卷交付方案（9,999 单）

所有数字来自 `platform_score.evaluate`（与该模型下官方子分同口径）。该方案即
`deliverables_semi/复赛结果_棒材优化.zip` 的内容：

| 指标 | 数值 |
|---|---:|
| 方案数 | 1,855（**没有做任何轮次合并**：`--no-merge` 逐字节原样交付，见下） |
| 冷床轮数 | 9,914 |
| 刀数 | 176,563 ⚠️ 取整口径未决，见 §6.6（`nearest` 读法为 185,577） |
| 成材率（评分分子，超产不计入） | 89.80% |
| 组合覆盖率 | 100.00%（9,999 / 9,999 单参与过多订单轮次） |
| 规则违规 | 0（含 clause 6 接续 0 条、订单跳轮 0 条） |
| 申报钢坯总量 | 557,846,737 kg |
| 实际超产量 | 14,539,962 kg（相对「向上取整的需求」计，占成品 2.87%）；相对**精确**需求计为 14,436,911 kg（2.59%），§6.5 的四分解用后者 |
| 本地模型总分 | 93.187（B=160,000）/ 77.329（B=90,000）⚠️ 绝对值为区间，见 §6.7 |

**为什么这一版不做轮次合并。** 上一版用 `build_submission.py` 的 `merge_compatible`
把 5,000 个定形方案按同钢种/同直径/同坯型装箱合并成 2,196 个。合并本身是保物理量的——
它校验三条不变量后才落盘：① 逐轮指纹（每轮的 `length_scheme × 并列支数 × 钢坯根数`）
与合并前完全相同；② `knives / rounds / finished_weight / blank_weight` 不变；
③ 覆盖率不下降。问题在于它**只顾了物理量、没顾 clause 6**：合并把不同源方案的轮
首尾相接地拼进同一个方案，而 clause 6 是对**方案内相邻轮**的约束，于是拼接缝两侧的
订单集合不同（表现为「方案 1 恰好缺批 3」），缝之外的整片却违规。**7,559 条即由此而来。**
本版交付路径改为 `--no-merge`：源方案已是定形器保证合规的最终方案集，逐字节写盘，
**校验的对象 = 提交的对象**（§5.4）。

**两个刀数口径。** 交付 JSON 上会看到两个不同的刀数，这是口径差异而非矛盾：
`platform_score.row_segments(convention='floor')` 按 **`int(L // size)`** 计段，
而导出写的是 `round(k * size, 9)` —— 实测 **39.8%** 的 `(k, size)` 组合上
`floor` 会比 `k` 少 1，于是计费刀数（**176,563**）低于 `validate_plan` 的朴素计数
（**185,577**）。该差额（**9,014 刀 = 5.1%**）是本方案**最大的单项不确定性**，两种读法
对总分的差为 0.99（B=90k）~ 1.20（B=180k）分，完整分析见 §6.6；本报告不把这份折扣
计入任何"预期收益"。

**单块实验的外推一致性。** §5.3 的单块实验（`NP01:43` 前 60 单）测得重定形后
1,019 刀 = 17.0 刀/单，按比例外推 9,999 单得 **170,000 刀**，与全卷实测
**176,563 刀** 相差 3.9%；同一实验对原搜索测得 2,546 刀 = 42.4 刀/单，
外推 **424,000 刀**。两个方向都吻合，说明刀数差距来自「并列支数取小」这一个
系统性选择，而不是分块噪声或抽样偏差。

### 6.2 超产允量 `r` 的扫描（本轮**方向反转**）

`r` 是**求解设置**（题目未给超产上限，见 §3.1），因此把它当参数扫描。每个 `r`
都重新构建一次全卷方案（定形窗口随之放宽），再由真实评分器在各自 λ 网格上取最高分。
下表每一格都由 `diagnostics/semi_hypothesis_table.py` 重算。⚠️ **`r = 0.02 / 0.05` 两行不干净**：
窗口太窄时定形器装不下全部订单，实测 `violation_count = 453 / 24`（覆盖 93.36% / 99.73%），
因此这两行只作曲线左端的参照，**不是可交付方案**，且下表的分数列**未计入违规罚分**
（若计入，`−5 × 453 / −5 × 24` 会再扣 2,265 / 120 分）；`r ≥ 0.10` 的四行
`violation_count = 0`、覆盖率 100.00%，另有 `platform_check` 独立通过：

| 每单超产允量 `r` | 刀数 | 成材率 | 实际超产（重量占比） | S(B=90k) | S(B=180k) | S(权重 0.4/0.4/0.2/0) |
|---|---:|---:|---:|---:|---:|---:|
| 0.02 | 243,721 | 91.61% | 0.91% | 70.927 | 85.698 | 70.088 |
| 0.05 | 209,423 | 91.10% | 1.74% | 74.465 | 91.655 | 73.574 |
| 0.10 | 184,363 | 90.30% | 2.38% | 76.617 | 96.143 | 75.647 |
| **0.25（交付）** | **176,563** | **89.80%** | **2.80%** | **77.329** | **96.939** | **76.309** |
| 0.50 | 175,853 | 89.90% | 2.78% | 77.441 | 96.970 | 76.431 |
| 1.00 | 175,603 | 89.89% | 2.79% | 77.467 | 96.966 | 76.456 |

四条读法：

1. **曲线在本轮是单调上升的，与前稿结论方向相反。** 前稿（旧定形族）认为
   「`r ≥ 0.10` 后已饱和」；在合规族上，`r` 从 0.02 放到 0.25 换回 **+6.40 分**
   （B=90k），放到 1.00 再换 +0.14 分。机制见 §4.3：合规化把「一单占几轮」锁成
   区间之后，刀数的主导量从「并列支数取小」变成**行数**，而 `r` 决定定形器能把
   多少行并成一行—— `r` 越宽，可共用的整数倍越大，行数越少；
2. **交付选 `r = 0.25`**：它拿到曲线 96% 的收益（相对 `r = 1.00` 只差 0.14 分 /
   B=90k，约 0.18 分 / B=160k），**名义允量却小一个量级**。
   ⚠️ 这里必须把两件事分开说：`r = 0.25` 的**实际**超产量（2.80%）与
   `r = 0.50 / 1.00`（2.78% / 2.79%）**几乎没有差别** —— 实际用量被「整根钢坯
   向上取整」的粒度卡住，并不随名义允量线性增长。所以选 0.25 的理由是
   **保守的名义承诺**（若官方另有隐性超产上限，25% 比 100% 更容易站得住），
   而不是「实际更省料」。本报告不把这两个口径混用。
3. **实际超产量远小于名义允量**（0.25 换 2.80%），因为 `K_i = ⌈P_i / p⌉`
   只在「再大一档并列支数恰好还落在窗口内」时才用掉这份自由度，而不是把每一单
   都顶到上限。这也解释了为什么放宽 `r` 的代价（成材率分母变大）能被真实计价、
   却仍然净赚。⚠️ 超产量有三个**分母**读法，是同一个分子的 2.80%（比未封顶成品重，
   本表口径）/ 2.87%（比向上取整的需求重，`提交说明.md` 口径）/ 2.59%（比申报原料重，
   §6.5 口径），不要混用。
4. ⚠️ **λ 选点的口径差异**：除交付行（12 点扫描，λ = 4800，**内部**最优）外，
   其余各行建于 λ 网格上限仍为 3200 时，选点落在**网格边缘**，故那几行的刀数
   **略偏保守**。用交付行自身的 λ 曲线估这个偏差：3200 → 4800 只值 **+0.004 分**，
   4800 → 9600 反而 −0.020 分，即边缘效应 **≲ 0.02 分**，不影响上表排序与结论。

### 6.5 剩余优化空间（"是否已到极限"）

`diagnostics/semi_headroom.py` 对交付方案做了一次分解，并以 `platform_score.evaluate`
为质量真源复算（四项质量分解残差 0.00）。结论：**算法意义上已到极限，绝对意义上
还差一个口径（§6.6）。**

**刀数轴。** 总刀数 = 段数 + 轮数 = 166,649 + 9,914 = **176,563**。

- **段数已经到（甚至低于）物理下界。** 下界 `Σ P_i / 并列上限` = 168,837，而计费口径的
  实收段数 166,649 比它低 **1.3%**；差的 9,014 刀来自 §6.6 的取整口径。真实物理切段数
  175,663 只比下界高 **4.0%**，这部分余量由「每轮至少 1 根」与整数装填强制产生，不可消除；
- **轮数余量已被压到 11.8%。** 9,914 轮 vs 按质量下界 8,870 轮（`物理坯重 / 60 t`），
  余量 **11.8%**（按净长下界 6,591 轮则余量更大，但质量口径更紧）。⚠️ 与前稿不同，
  本轮轮子**基本是满的**：净长中位数已占长度上限的 **0.95**、质量中位数占 **0.97**，
  9,490 / 9,914 轮是被**重量**卡住（60 t 比 150 m 更紧），占满 >98% 的轮达 **40.2%**。
  这正是 clause 6 加 `r = 0.25` 的直接结果：定形器把行并进轮里，轮就不再空转。
  λ 扫描给出这条边际曲线：λ 从 4800 走到 9600 只省 **205 刀**，却损失 **0.21 个成材率
  百分点**，折分 **93.187 → 93.167（净分为负）**。所以轮数余量"存在但已不值得取"。

**成材率轴。** 原料钢坯精确四分（残差 0.00）：

| 去向 | 质量 | 占原料 |
|---|---:|---:|
| 计入分子（受需求量封顶） | 500,935,599 kg | 89.80% |
| 超产（λ 与 `r` 可调） | 14,436,911 kg | 2.59% |
| 共享修边 2 m/轮（规则强制） | 11,024,662 kg | 1.98% |
| 未切尽（整根坯向上取整） | 31,449,565 kg | 5.64% |

⚠️ 与旧包相比，**未切尽**由 4.19% 升到 **5.64%**、**超产**由 1.56% 升到 **2.59%** ——
这是合规化的另一笔代价：区间结构迫使订单集中到更少的轮里，整根坯的取整损失随之变大。
其中**只有 2.59% 是选择**；1.98% 由「每轮 2 m 头尾」强制，5.64% 由「只允许整根钢坯」
强制，两者合计 **7.62% 结构性不可约**。若整根取整不损料，成材率上限
`500,935,599 / (515,372,509 + 11,024,662) = 95.16%`；若修边也不损料，上限 **97.20%**。
这是规则下的物理天花板，与算法无关。

**"是否到极限"的三条证据。** (1) λ 的 12 点扫描给出**内部**最优 λ = 4800
（相邻点 93.183 / 93.176 / 93.167），是该定形族内的解析最优——但这一条**只在基准刀数
B = 160,000 的取法下成立**，选点随 B 移动，见 §6.7；
(2) 把配对窗口从 4 加倍到 8（`runs/pair8`，旧定形族）输出的回合逐条完全一致。**这一条
比前稿的表述弱**：`pair_group` 是"遇到第一个可行配对即停"的贪心（`build_semi_plan.py:59`），
窗口加倍只是让该贪心**在自身参数上饱和**，不等于配对已最优；配对自由度本身几乎不受约束——
`diagnostics/semi_coverage_ceiling.txt` 显示 36 组共 9,963 对相邻订单**全部 100% 可共享轮次**
——真正的取舍发生在配对之后整根坯的取整损失上。故本条降级为"贪心政策饱和"，不再作为
最优性证据；
(3) `r` 从 0.10 放大到 1.00 值 **+0.85 分**（B=90k）——**与前稿相反，`r` 轴并未用尽**，
只是收益递减（0.10 → 0.25 占掉 **+0.71**，0.25 → 1.00 只剩 **+0.14**）。第 (1)(3) 条支持
"结构上已无大项可动"，第 (2) 条只支持"该贪心不再自行改进"。

**结构性未探索项（据实列出，避免把"当前实现的最优"说成"问题的最优"）。** 除基准刀数外，
当前实现还有两处**已知的、有意的**收窄：

| 收窄处 | 代码位置 | 影响 |
|---|---|---|
| 装桶为贪心 + 桶间交换，不做全局最优装箱/重排 | `build_semi_plan2.py:153` `cap_aware_bins` / `:205` `balance_bins` | 装桶只影响整根坯取整损失与可行的 `(m,R)`，量级小；非贪心装箱仍有理论余地 |
| 每个方案内**所有轮共用同一并列支数** `p` | `continuity_shaper.py` 的 `scheme_candidates`（`for p in range(1, parallel_limit+1)`） | 格式（`counts` 为逐轮列表）本允许逐轮异构 `p`，实现未探索；异构轮次可望改善轮内装填 |

这两项**不改变本报告的任何已交付数字**，但它们是"尚未证明全局最优"的具体来源。方向性的
后续优先级见 §7 第 8 条：先把评分口径钉死，再谈装桶与异构轮次。

### 6.6 主导一切的一项：刀的取整口径（`int(L//size)` vs `nearest`）

本次复核发现的**单项影响最大**的未决事项，量级超过全部 λ、r 与装桶余量之和。

`solver` 导出方案时写 `round(k × 定尺, 9)`；这个 9 位小数在某些 (k, 定尺) 组合上会落到
整数下方（如 `18.0 / 3.6 = 4.999999999999999`），于是**同一份方案**有两种读法：

| 读法 | 段数 | 总刀数 | 刀分子分 (B=90k) | 总分 (B=90k) |
|---|---:|---:|---:|---:|
| `int(L // size)`（`row_metrics` 的计费口径） | 166,649 | **176,563** | 50.97 | **77.3287** |
| `nearest`（`platform_check` 的收件口径） | 175,663 | **185,577** | 48.50 | **76.3384** |

差异 **9,014 刀 = 5.1%**，B=90k 下值 **0.99 分**、B=160k 下值 **1.76 分**、
B=180k 下值 **1.20 分**（不比 160k 高，因为此时刀项已封顶，两种读法都拿满分）。
六个 `r` 全表复算（与 §6.3 同源脚本）：

| r | 刀数(floor) | 刀数(nearest) | ΔS(B=90k) | ΔS(B=180k) |
|---|---:|---:|---:|---:|
| 0.02 | 243,721 | 252,893 | +0.536 | +1.071 |
| 0.05 | 209,423 | 218,564 | +0.719 | +1.438 |
| 0.10 | 184,363 | 193,286 | +0.901 | +1.803 |
| **0.25（交付）** | **176,563** | **185,577** | **+0.990** | **+1.202** |
| 0.50 | 175,853 | 184,795 | +0.991 | +1.038 |
| 1.00 | 175,603 | 184,547 | +0.994 | +0.986 |

**两种读法下 `r` 的排序不变**，`r = 0.25` 与最优相差仍 ≤ 0.14 分——§6.2/§6.3 的**选点
结论稳健**；但**绝对分数不可自信引用**：B=90k 时是真 77.33 还是 76.34，取决于平台实际
用哪一种取整。

哪一种更可能？`platform_check` 用 `nearest` 判定交付，而这**几乎是唯一可能的口径**：
若平台对交付也用 `int(L//size)`，则 39.8% 的 (k, 定尺) 组合都会被判「少交 1 件」，
几乎所有方案都会爆违规，显然不成立。既然平台对**交付**必须宽容，它对**计刀**大概率
也宽容，因此 **`nearest`（185,577 刀）更可能是平台的真实口径**。本报告保留两种读法的
全部数字，不单选一个当作官方预测。

我们**刻意没有**去利用 `int(L//size)`：把每段长度写到整数倍下方 1e-15，理论上可使分段
计费归零（刀分子分封顶 100，B=90k 下凭空 **+19.6 分**），但这是在利用评分器的浮点表示
而非求解优化问题，且一旦平台口径自洽（对交付也 floor），会导致大面积「少交」违规。
当前方案自带的 **5.13%** 折扣只是 `round(…, 9)` 的**自然浮点落点**，不是刻意构造，
也不计入任何"预期收益"。

### 6.7 更正：λ 的选点依赖基准刀数

**本节更正本报告前稿的一句话。** 前稿在 §0 与 §9 写过"`r` 与 λ 的选点结论在两种口径下
完全一致"，该表述**不成立**：它只被验证于"刀口径 × B=90k/180k"这四格，而 λ 的选点是
**随基准刀数 B 移动的**。

机制很清楚。刀数子分为 `40 · min(1, B / K)`，于是

* B 变大（尚未封顶时）会**线性放大"每省一刀值多少钱"**，而成材率项 `0.3 × 成材率`
  完全不受 B 影响 ⇒ 刀/料权衡的最优点**右移**（多省刀、多耗料）；
* B 大到 `B ≥ K` 时刀项封顶为 40（满分），刀数再多也无收益 ⇒ 目标退回"纯成材率"，
  最优点**左移**回成材率最高的一侧。

独立校验器会去读初赛目录（`build_submission.py` 的 `--data` 默认为 `data`），属静默用错数据。
在交付包里对应的命令见 `环境与复现说明.md` §3（路径改为 `code/`、`PYTHONPATH=code`）。

**运行环境**：Python 3.10+，**仅使用标准库**（`math` / `json` / `csv` / `zipfile` /
`decimal` / `itertools` / `collections` / `pathlib` / `tempfile` / `hashlib` / `argparse`），
无第三方依赖；Windows / Linux 均可运行。本报告全部结果在
**Python 3.13.12（Windows 11）** 上产出。

## 9. 结论

**本轮的核心不是「多了一条连续性约束」，而是「判据被官方驳回一次后，把它反推出来、
重造定形器、并把合规的代价完整计价」。**

上一版被平台判为**不可行、总分 = 0**，`跨轮接续不连续` **7,559 条**。根因是旧定形器
`round_shaper` 把每个订单放进**每一轮**，于是方案内任意相邻两轮的订单集合完全相同，
逐条命中 clause 6；`merge_compatible` 的拼接缝则把违规切成了官方串里
「方案 1 恰好缺批 3」那段不可伪造的指纹。本版的做法是（§5.4）：从**两条官方反馈 +
题面输出示例**反推出判据 C（相邻两轮集合不得完全相同）与跳轮禁令，写进
**不读求解器代码**的 `diagnostics/semi_continuity_audit.py`——它在旧包上复现出
7,559 条、在本包上给出 0 条——再把定形器换成 `continuity_shaper.py`
（枚举 `(m, R)` 的**全部**合法区间结构，只作**必要条件**剪枝，并用
3,967 次随机暴力对拍验证 0 处不一致）。

**合规不是免费的，代价被完整计价而不是掩盖。** 以同一 `r = 0.10` 比较：
刀数 175,952 → 184,363（+4.8%）、成材率 91.81% → 90.30%，折 **−2.11 分**（B=160k）。
旧包刀数更低，恰恰因为它做出了共享率最高但**违规**的轮。在合规族内重扫 `r` 之后，
`r = 0.10 → 0.25` 换回 **+1.38 分**（代价：成材率 −0.50 个百分点、名义超产允量
10% → 25%），净效果相对旧包为 **−0.73 分**，而旧包的实际得分是 **0**。

**另外三处口径翻转仍成立**：计刀从「每单加头尾」改为「每轮一组头尾」、成材率分子
从「含超产」改为「不含超产」、覆盖率从「同批」收紧为「同轮」。它们解释了为什么
「按同交付量取最小并列支数」的旧启发式恰好在反方向优化——§3.2 给出该**一个**
系统性选择值约 25 万刀。

**交付结果**（`platform_score.evaluate`，B = 160,000）：**1,855 方案 / 9,914 轮 /
176,563 刀**（floor 读法；nearest 读法 185,577）/ 成材率 **89.80%** /
覆盖率 **100.00%** / `violation_count = 0`（clause 6 接续 0 条、订单跳轮 0 条）/
本地总分 **93.187**（B=160k）或 **77.329**（B=90k）。四道闸门全过：
`platform_check`（19 类错误全零）、`solver.validate_plan`、`platform_score.evaluate`，
以及数据侧的 `semi_continuity_audit`。全卷构建 **431 秒 / 16 进程**，**无随机数**，
同一参数独立重跑产出的 `result.json` 逐字节相同。

**是否已优化到极限？** 在**本实现**的既定策略与评分假设下**是**：λ 的 12 点扫描给出
**内部**最优 **λ = 4800**（相邻点 93.183 / 93.176 / 93.167），轮数余量只剩 **11.8%**，
且 **40.2%** 的轮已占满 >98%（§6.5）。绝对意义上**不是**，剩余不确定项可归为三类：

- **口径类（影响最大，且只能由平台反馈解决）**：刀的取整口径使同一份方案相差
  **9,014 刀（5.1%）**（值 0.99（B=90k）~ 1.76 分（B=160k），§6.6）；基准刀数 B 的
  复赛值虽已由群答疑给出为 160000（档案见 `evidence/rules/`），但**非官方书面文件**，
  且 **λ 的最优点随 B 移动**（§6.7）。这类不确定性不能由求解消除；
- **规则类**：成材率天花板被规则锁死——「只允许整根钢坯」占 **5.64%**、每轮 2 m 修边
  占 **1.98%**，合计 **7.62% 结构性不可约**，只剩 2.59% 的超产是选择（§6.5）；
- **实现类（已知、有意收窄，量级已验证很小）**：装桶是容量感知贪心 + 一次桶间交换，
  不做全局装箱；每个方案内**所有轮共用同一并列支数** `p`（`continuity_shaper.py` 的
  `scheme_candidates`），而格式本允许逐轮异构。这两项**不改变任何已交付数字**。

因此本报告**不使用"已达全局最优"的说法**，只使用"在该定形族与该装桶策略下达到
**稳定局部最优**"。

**对刀数与总分的表述一律给区间**：刀数 176,563（floor 读法）~ 185,577（nearest 读法）；
总分 B=90k 为 77.33 ~ 76.34、B=160k 为 93.19 ~ 91.43、B=180k 为 96.94 ~ 95.74
（§6.6 给出逐格差值，§6.7 给出各基准下的族内最优 λ）。
⚠️ **前稿此处写的"选点（`r = 0.10`、λ = 2400）在全部读法下不变"已更正**：
合规化之后 `r = 0.10` 已不再是稳健选点（§6.3），λ 的族内最优点也随 B 移动（§6.7）。
