# 棒材组合订单高效锯切优化 —— 复赛求解技术报告

**队名**：棒材优化　**轮次**：复赛　**交付日期**：2026-09-21

---

## 0. 摘要

本报告给出复赛（9,999 个有效订单）的完整求解方法与验证结果。求解器把问题分解为
「**按钢种/规格分组 → 组内配对 → 逐方案重定形 → 双目标选点**」四步，全部只用 Python
标准库，整卷构建约 **1 分钟**（对比之下，原随机邻域搜索约需 **46 秒 CPU / 60 单**，
外推全量要数小时，且会输出刀数高一倍的方案）。

在自建的**三层验证闸门**（独立物理校验器 `platform_check`、求解器自带
`validate_plan`、评分模型 `platform_score.evaluate`）下，最终方案：

| 指标 | 结果 |
|---|---|
| 有效订单覆盖 | **9,999 / 9,999**（源数据 10,000 单中 1 单为异常数据） |
| 物理/结构校验 | **通过，0 违规**（`platform_check` 19 类错误全为零） |
| 规则违规数 | **0**（`violation_count = 0`，无欠产、无跳轮、无超轮数） |
| 刀数 | **175,952**（5,000 个方案 / 12,559 轮）⚠️ 取整口径未决，见 §6.6 |
| 成材率 | **91.81%** |
| 组合覆盖率 | **99.99%**（9,998 / 9,999 单参与过多订单轮次） |
| 本地模型总分 | **78.00 / 97.54**（基准刀数 90,000 / 180,000）⚠️ 绝对值为区间，见 §6.6 |

> ⚠️ **刀的取整口径是本次最大的未决事项**：同一份方案在 `int(L//size)` 与 `nearest`
> 两种读法下相差 **14,389 刀（8.2%）**，B=90k 下值 **1.55 分**。上表刀数 175,952 用
> `int(L//size)` 口径；`nearest` 口径为 **190,341**（详见 §6.5 / §6.6）。`r` 与 λ 的
> **选点结论在两种口径下完全一致**。

本轮的三个关键结论（均带可复现证据）：

1. **复赛允许超产**。「超产不扣分、但不计入成材率分子」是本轮最重要的规则差异，
   它决定了整条求解路线；
2. **刀数是复赛的主战场，成材率是次要杠杆**。原方案在整卷尺度上的刀数子分仅约 20 分
   （满分 40），而成材率只差约 6 分；
3. **成材率的主要损耗来自「整根钢坯向上取整」**，而不是切损。原方案申报钢坯比物理
   需要量多 **18.0%**。

## 1. 问题与数据

### 1.1 数据规模

复赛订单原始文件 `data/semi/orders_semi.csv`（GBK 编码）共 **10,000** 行，其中
订单 **B20270281** 的「订单重量」为 **−25.418 t**，属非正重量异常数据，按题面允许的
异常过滤流程隔离，**不猜测其正确值、不虚构方案**。剩余 **9,999** 个有效订单构成本次
求解对象。10,000 行原始文件未被改动（`data/semi/data_audit.json` 记录隔离明细）。

订单按「钢种 + 规格（直径）」分为 **36** 个组，最大的组 `NP01:43` 有 **3,532** 单，
其次 `C60:26.5` 有 **2,205** 单。只有同钢种、同规格的订单才能组合（约束 5）。

### 1.2 复赛的 12 条约束

`data/semi/constraints.txt` 给出 12 条约束，可归为三类：

**设备与计量（第 1–4 条）**
1. 锯切辊道承载棒材最短 **50 m**，最长 **150 m**；
2. 辊道宽度 **2 m**；
3. 辊道最大承重 **60 t**；
4. 每个订单组合方案使用的冷床轮数不得超过 **6 轮**。

**业务规则（第 5–11 条）**
5. 订单须同钢种、同规格才可组合；
6. 同一订单若分在多轮锯切，必须在**相邻轮次连续**锯切，中间不得插入其他订单，不得跳轮；
7. 每轮冷床铸坯总重须**不低于**本轮棒材重；
8. 每订单冷床分配总重量须**不低于**该订单重量；
9. 订单每次分配长度须为该订单定尺长度的**整数倍**；
10. 同一订单不得跨方案重复出现；
11. 同一方案内订单号不得重复。

**完整性（第 12 条）**
12. 除异常订单外，**所有订单均须参加锯切计算**，否则每单计 1 次违规。

## 2. 评分模型口径

复赛评分沿用 PDF 第九页的权重表：

```
总分 = 0.40 × 刀数子分 + 0.30 × 成材率子分 + 0.20 × 覆盖率子分 + 0.10 × 时间子分
       − 5 × 违规次数
```

### 2.1 刀数子分

本轮计刀口径被赛题组**修正**过（`RULES.md` 第 23 行）：初赛「给每个订单都加头尾」，
复赛改为「**连接处算一刀，每轮冷床只有一组切头切尾**」。落到实现即：

```
每轮刀数 = Σ_订单 int(length // size) + 1
```

其中 `length` 是该订单在本轮申报的净长度（定尺整数倍），`size` 是定尺长度。
注意这里是**浮点整除**语义：导出时写 `round(k * size, 9)`，在某些 `(k, size)` 组合上
`round(k*size, 9) // size` 会比 `k` 小 1（实测占 39.8% 的组合），我们严格照抄这一
浮点行为，不做「修正」。

刀数子分 = `100 × B / 刀数`，其中**基准刀数 B 未获复赛官方确认**（初赛为 90000）。

### 2.2 成材率子分

```
成材率 = Σ_订单 min(该订单产出重量, 该订单需求重量) / Σ_轮 申报钢坯重量
```

**分子**是成品重量，复赛**剔除超产部分**（`RULES.md` 第 19、43 行；
超产部分「不计入成材率」）；成品重量按**直径截断到整数毫米**再算圆截面
（该口径由三份初赛官方反馈复现得到）。**分母**是各轮申报钢坯重量之和，
两端各 1 m 的固定切损计入承重校验、也进分母。

### 2.3 覆盖率子分

初赛「同一批内不同轮次切过即可」在复赛被**收紧**：必须**在同一轮次共同上冷床**
才能算有效组合（`RULES.md` 第 21 行、答疑 09-14 15:45）。
因此覆盖率 = 参与过「多订单轮次」的订单数 / 有效订单数。

### 2.4 未决口径

- **刀数基准 B**：复赛未公布。初赛为 90000。本报告同时在 B = 90000 与
  B = 180000（按订单规模线性外推）两种假设下给出结论，见 §6.3；
- **时间子分**：同一页 PDF 上存在**两种互相冲突的表述**——正文写 40% / 30% / 20% / 10%
  （时间独立占 10%），紧接着的**公式**却写 `40 × 基准刀数/总刀数 + 40 × 成材率
  + 20 × 覆盖率`，即 40/40/20、**根本没有时间项**（`README.md` 第 165 行记录了这处矛盾）；
  群答疑又称「时间并入成材率子项」（`RULES.md` 第 25、47 行）。本报告以 PDF 正文版
  （独立 10%）为主口径实现，并在 §6.3 用 (0.4, 0.4, 0.2, 0) 对「无时间项」版做了对照——
  后者在数值上同时等价于「时间并入成材率」的说法，结论不变；
- **时间子分若被实测**：本模型按满分 100 计（`Rules.time_subscore = 100.0`）。
  我们没有官方的时间标尺，只能给出可比的绝对量级——交付方案从原始数据到成品提交包
  的**实测墙钟约 75 秒**（§4.5），对比原分块搜索的近 2 小时，即使官方按运行时间打分，
  也应是接近满分的量级。

## 3. 三个关键发现

### 3.1 复赛允许超产（决定路线的一条）

约束 7、8 都是**单边下界**（「**不低于**」），12 条中没有一条禁止超产。`RULES.md`
第 18、19 行进一步明确：

> 复赛：**改为欠产惩罚**（少生产扣分）；**超产不扣分，但超产部分不计入成材率**。

四条独立证据：

1. `constraints.txt` 第 7、8 条为「不低于」的单边下界；
2. `RULES.md` 第 18 行「超产不扣分」、第 19 行「成材率分子不包含超产成品」；
3. 独立校验器 `platform_check.py` 的 **19 类 error kind 中没有超产类**，
   且第 215–220 行注释明确写道：「超产不是 checker 的违规，
   超产扣分住在 `platform_score.Rules.numerator_capped_by_demand`」；
4. `platform_score.evaluate` 对分子逐单封顶（`min(产出, 需求)`）。

**这一条的实际含义**：超产**只通过分母惩罚自己**（多产 → 多申报钢坯 → 成材率下降），
不存在额外罚分。因此「允许少量超产」是一个合法的**求解设置**，其代价可以在评分模型内
被精确计价 —— 这为 §4.3 的「重定形」提供了关键自由度。

### 3.2 刀数在整卷尺度远未触顶 —— 它才是主战场

早期结论认为「`40 × min(1, 90000/刀数)` 恒被饱和，所以刀数对搜索不可见」。
该结论**只在单个分块内成立**：分块只有 60 单，刀数约 2,700，远小于 90000。
但评分是在**整卷**上计算的：

```
整卷刀数 K ≈ 450,000   （由 60 单分块实测 2,546 刀外推）
刀数子分 = 100 × 90000 / 450000 ≈ 20   （满分 100）
```

即刀数一侧损失 `0.4 × (100 − 20) = 32 分`，而成材率一侧（0.82 对 1.0）
只损失 `0.3 × 18 = 5.4 分`。**刀数是量级更大的杠杆。**

这个外推在 §5.3 的单块实验里被证实，并在全卷求解完成后闭环：重定形把单块刀数
从 2,546 降到 1,019（17.0 刀/单），按比例外推 9,999 单得 **170,000 刀**，
与全卷实测 **175,952 刀** 相差 3.4%（§6.1）。也就是说，「并列支数取小」这**一个**
系统性选择就值约 **25 万刀**，折合 **12 分**（B=90,000）到 **23 分**（B=180,000）。

### 3.3 成材率的主要损耗是「整根钢坯向上取整」，不是切损

每轮的钢坯约束是

```
blank_count × usable ≥ total × parallel,   usable = blank.weight / μ
⟹ blank_count = ⌈ total × parallel / usable ⌉
```

由于 `usable` 很大（`BT5` @ φ43 → 615.9 m/根），而一轮实际只需约 0.9 根，
向上取整到 1 根就凭空多申报一整根钢坯。实测原方案：

```
申报钢坯总量 / 物理需要总量 = 3,249,574 / 2,753,523 = 1.1802
```

**18.0% 的申报钢坯是纯粹的取整余量**，远大于 2 m/轮 的共享切损（约 2.5%）。
这就是成材率被压在 0.823 的直接原因。

重定形（§4.3）之后，交付方案的申报钢坯总量降到 **545,633 t**，成材率随之从 0.823
升到 **0.918**；剩下的 8.2% 差额就是「2 m/轮 共享切损 + 残余的整根取整余量」。
换算到分数：成材率一侧的损失从 `0.3 × 17.7 ≈ 5.3 分` 压到 `0.3 × 8.2 ≈ 2.5 分`。

## 4. 算法

### 4.1 总体结构

```
9,999 单
  │  ① 按 (钢种, 规格) 分组            → 36 组
  │  ② 组内邻居优先配对（2 单/方案）   → 5,00x 个方案
  │  ③ 每个方案枚举 (坯型, n, parallel) → 帕累托候选集
  │  ④ 用 Lagrange 乘子 λ 在双目标上选点
  ▼
result.json（platform_check / validate_plan 双闸门通过）
```

### 4.2 配对：只需要「谁能和谁共享轮次」

原搜索 `search_10s` 用约 46 秒 CPU（每 60 单）同时决定**配对**与**每轮形状**。
但我们发现：**形状可以脱离搜索被直接最优求解**（§4.3），而配对在评分中
**只通过覆盖率起作用** —— 覆盖率要求「同一轮次共同上冷床」，而重定形会把一个方案的
**每个订单都放进它的每一轮**，所以只要一个方案里有 2 个订单，这 2 单就必然互相贡献覆盖。

于是配对退化成一条极简策略：组内按原始顺序，把当前订单与后续若干订单（默认看
4 个）中**第一个存在合法形状**的配对；都不行则单独成方案（约束 12 的完整性优先于覆盖率，
与原 `_pack_group` 的取舍一致）。

实测：**60 单配对 0.09 秒**；全卷 5,000 个方案在 `r = 0.02` 下 **26 秒**、在交付口径
`r = 0.10` 下 **63 秒**（候选枚举随 `r` 变宽），35 个组中仅 **1 个订单**落单
（`C60:26.5`），覆盖率 99.99%。

### 4.3 逐方案重定形：把「怎么分轮」和「交多少件」解耦

对一个方案内的订单集合，设订单 `i` 的需求件数为 `P_i`，允许上限
`C_i = P_i + ⌊P_i × r⌋`（`r` 为超产允量）。**关键简化**：

> 若 `n` 轮使用**同一个** `parallel = p`，则订单 `i` 得到的件数是 `K_i × p`，
> 其中 `K_i` 是订单 `i` 在单根棒材上的**总段数**。
> **件数与「怎么把这 `K_i` 段摊到 `n` 轮」完全无关。**

由此得到两个解耦的决策：

**决策一：`K_i` 取最小合法值。** 需求窗口 `[P_i, C_i]` 逐单独立，所以

```
K_i = ⌈ P_i / p ⌉        且要求   K_i × p ≤ C_i
```

就是该 `p` 下刀数最小的合法段数（段数越少刀越少）。

**决策二：`n` 取最小可行值。** 因为刀数 = `Σ_i K_i + n`，而件数与 `n` 无关，
`n` 只需保证**每一轮都落在床的合法区间内**。设

```
cap_len = min(150, 60000 / (p × μ))        # 床长上限与承重上限的联合
S = Σ_i K_i × size_i                       # 单根棒材上的总成品长度
```

把 `S` 摊到 `n` 轮，则每轮长度为 `2 + S/n`，必须落在 `[50, cap_len]`，于是

```
n × (50 − 2) ≤ S ≤ n × (cap_len − 2)
```

枚举 `n ∈ [n_lo, n_hi]`，对每个 `n` 用一次贪心均衡分配 + 越界回填把 `Σ_i K_i`
摊到各轮（`parts[i][r] = K_i // n + (1 if r < K_i % n else 0)`，再按最重/最轻轮
互相搬运，200 步内不收敛就丢弃该 `n`），最后按 `(刀数, 申报钢坯)` 做帕累托裁剪。
由于刀数与申报钢坯都随 `n` 单调不减，边界上实际只留下最小的几个 `n`。

**这一条是原方案的主要缺口。** 原搜索对同一个「交付件数向量」只保留**最小**的
`parallel`（`_enumerate_round_shapes` 中 `if old is not None and parallel >= old[0]: return False`，
`parallel` 循环升序 → 留下第一个即最小者）。但复赛每轮刀数是 `Σ段数 + 1`，
而该轮段数为 `Σ(delta_i / parallel)`，**同一个交付量下 `parallel` 越大刀越少**。
保留最小值正好把刀数最大化了。

### 4.4 双目标选点：为什么成材率只需最小化申报钢坯

因为所有合法候选都交付 `≥ P_i` 件，按 §2.2 的封顶口径，**计入分子的重量恒为
`Σ_i P_i × size_i × μ_int`，是一个常数**。于是

```
成材率 = 常数 / Σ_方案 申报钢坯
```

即：**最大化成材率 ⟺ 最小化申报钢坯总量**，刀数则要最小化 `Σ n`。整卷权衡因此
退化为一个干净的双目标问题 `(Σ刀数, Σ申报钢坯)`。实现用 Lagrange 乘子扫描：

```
每个方案取   argmin( 申报钢坯 + λ × 刀数 )
```

`λ` 的物理含义是「1 刀值多少公斤钢坯」。对全卷扫描 λ 并**用真实评分器
`platform_score.evaluate` 实测每个 λ 的总分**，取最高者；由于候选集只算一次、
可被所有 λ 复用，一次 9 点扫描只多花几秒。

| 原 `search_10s` | 46 s CPU | 约 167 块 × 46 s ≈ **2.1 h** CPU |

交付链路**实测墙钟**（本机 Windows 11 + Python 3.13.12，16 核但全程单进程）：

| 步骤 | 实测 |
|---|---:|

即**从原始 GBK 数据到可提交的 ZIP 全程约 75 秒**，而原分块搜索约需 2 小时。

单方案候选枚举为 `坯型(5) × parallel(≤ 46) × n(≤ 6)`，每点 O(订单数)，
一次 `_split_rounds` 均衡可在数十次内收敛，因此单方案是毫秒级。

### 5.2 三层验证闸门

1. **`platform_check.check`** —— 从原始 GBK CSV 与提交 JSON 独立重算：
   整数倍长度、含余量的床长/承重、床宽、交付数量、钢坯物料、条款 7/8 下界、
   连续性、覆盖率。本轮结果：**`passed = True`，19 类错误全为零**；
2. **`solver.validate_plan`** —— 用与 `make_round` **不同的独立实现**重算约束与成本

   订单质量下界、跨方案唯一性、连续性。本轮结果：**通过，12,559 轮，覆盖率 99.99%**
   （其对刀数的朴素计数为 190,341，与平台计费口径 175,952 的差额即 §6.6 的取整口径问题）；
3. **`platform_score.evaluate`** —— 评分模型。本轮结果：**`violation_count = 0`**。

此外 `build_submission.py` 在打包后会**重新打开 ZIP 内的实际字节**再跑一遍

## 6. 结果

### 6.1 全卷交付方案（9,999 单）

所有数字来自 `platform_score.evaluate`（与该模型下官方子分同口径）。该方案即
`deliverables_semi/复赛结果_棒材优化.zip` 的内容：

| 指标 | 数值 |
|---|---:|
| 方案数 | 2,196（打包时把 5,000 个定形方案按同钢种/同直径/同坯型装箱合并，见下） |
| 冷床轮数 | 12,559 |
| 刀数 | 175,952 ⚠️ 取整口径未决，见 §6.6（`nearest` 读法为 190,341） |
| 成材率 | 91.81% |
| 组合覆盖率 | 99.99%（9,998 / 9,999 单参与过多订单轮次） |
| 规则违规 | 0 |
| 申报钢坯总量 | 545,633,120 kg |
| 实际超产量 | 8,508,433 kg（占成品 1.67% / 占原料 1.56%） |
| 本地模型总分 | 78.001（B=90,000）/ 97.540（B=180,000）⚠️ 绝对值为区间，见 §6.6 |

**关于方案数。** `build_semi_plan.py` 产出 5,000 个两单方案；`build_submission.py`
的 `merge_compatible` 只做**装箱重排**：把同 `(钢种, 直径, 坯型)` 的整方案塞进
`≤ 6` 轮的箱子再拼接。它校验三条不变量后才落盘——① 逐轮指纹（每轮的
`length_scheme × 并列支数 × 钢坯根数`）与合并前完全相同；② `knives / rounds /
finished_weight / blank_weight` 不变；③ 覆盖率不下降。所以合并只改变 `orders`
列表的分组，不改任何物理量（这也是「覆盖率只取决于谁和谁同轮」的直接结果）。

**两个刀数口径。** 交付 JSON 上会看到两个不同的刀数，这是口径差异而非矛盾：
`platform_score.row_segments(convention='floor')` 按 **`int(L // size)`** 计段，
而导出写的是 `round(k * size, 9)`——实测 **39.8%** 的 `(k, size)` 组合上
`floor` 会比 `k` 少 1，于是计费刀数（**175,952**）低于 `validate_plan` 的朴素计数
（**190,341**）。该差额（14,389 刀 = 8.2%）是本方案**最大的单项不确定性**，两种读法
对总分的差为 1.55~2.17 分，完整分析见 §6.6；本报告不把这份折扣计入任何"预期收益"。

**单块实验的外推一致性。** §5.3 的单块实验（`NP01:43` 前 60 单）测得重定形后
1,019 刀 = 17.0 刀/单，按比例外推 9,999 单得 **170,000 刀**，与全卷实测
**175,952 刀** 相差 3.4%；同一实验对原搜索测得 2,546 刀 = 42.4 刀/单，
外推 **424,000 刀**。两个方向都吻合，说明刀数差距来自「并列支数取小」这一个
系统性选择，而不是分块噪声或抽样偏差。

### 6.2 超产允量 `r` 的扫描

`r` 是**求解设置**（题目未给超产上限，见 §3.1），因此我们把它当参数扫描。每个
`r` 都重新构建一次全卷方案（重定形窗口随之放宽），再对 9 点 λ 并用真实评分器取
最高分。全 9 点 λ 的逐点明细（交付口径 `r = 0.10`）存档在
`diagnostics/semi_lam_sweep_r010.txt`，关键两行：`lam=2400 → knives=175,952 /
score=78.001`、`lam=3200 → knives=175,291 / score=77.985`（§6.5 引用的那条边际曲线）。
下表每一格都由 `diagnostics/semi_hypothesis_table.py` 重算（含未决口径，见 §6.3），
所有方案 `platform_check` 通过、违规恒为 0：

| 每单超产允量 `r` | 刀数 | 成材率 | 实际超产（重量占比） | S(B=90k) | S(B=180k) | S(权重 0.4/0.4/0.2/0) |
|---|---:|---:|---:|---:|---:|---:|
| 0.02 | 211,356 | 92.11% | 0.89% | 74.659 | 91.692 | 73.870 |
| 0.05 | 178,735 | 91.81% | 1.44% | 77.682 | 97.540 | 76.863 |
| **0.10（交付）** | **175,952** | **91.81%** | **1.67%** | **78.001** | **97.540** | **77.181** |
| 0.25 | 174,994 | 91.72% | 1.82% | 78.085 | 97.513 | 77.256 |
| 0.50 | 174,785 | 91.69% | 1.84% | 78.103 | 97.506 | 77.273 |
| 1.00 | 174,741 | 91.69% | 1.85% | 78.108 | 97.506 | 77.277 |

三条读法：

1. **曲线在 `r = 0.10` 之后基本饱和。** 从 0.02 到 0.10 换回 **+3.34 分**

2. **交付选 `r = 0.10`**：它在四种未决口径下**都不劣**（最差的一格也只差 0.25 分），

3. **实际超产量远小于名义允量。** 名义 10% 换来的实际超产只有 1.67%（按重量），

   分母变大）能被真实计价却仍然净赚。

### 6.5 剩余优化空间（"是否已到极限"）

`diagnostics/semi_headroom.py` 对交付方案做了一次分解，并以 `platform_score.evaluate`
为质量真源复算（四项质量分解残差 0.00）。结论：**算法意义上已到极限，绝对意义上
还差一个口径（§6.6）。**

**刀数轴。** 总刀数 = 段数 + 轮数 = 163,393 + 12,559 = **175,952**。

- **段数已经到（甚至低于）物理下界。** 下界 `Σ P_i / 并列上限` = 168,837，而实收
  段数 163,393 比它低 **3.2%**；差的 14,389 刀来自 §6.6 的取整口径。真实物理切段数
  177,782 只比下界高 5.3%，这部分余量由「每轮至少 1 根」与整数装填强制产生，不可消除；
- **轮数是唯一有量级余量的一项。** 12,559 轮 vs 按质量下界 8,810 轮（`物理坯重 / 60 t`），
  余量 42.6%。但轮子并不空：净长中位数只占长度上限的 **0.68**，11,046 / 12,559 轮是被
  **重量**卡住（60 t 比 150 m 更紧），占满 >98% 的轮只占 **2.5%**。更关键的是把轮数
  压向质量下界需要往同一轮塞更多订单，而每方案封顶 6 轮、订单轮次必须连续——这会推高
  `K_i` 与成材率损耗。λ 扫描已给出这条边际曲线（175,952 → 175,291）：**再省 661 刀要
  付出 0.31 个成材率百分点，净分为负**。所以轮数余量"存在但已不值得取"。

**成材率轴。** 原料钢坯精确四分（残差 0.00）：

| 去向 | 质量 | 占原料 |
|---|---:|---:|
| 计入分子（受需求量封顶） | 500,935,599 kg | 91.81% |
| 超产（λ 可调） | 8,508,433 kg | 1.56% |
| 共享修边 2 m/轮（规则强制） | 13,351,098 kg | 2.45% |
| 未切尽（整根坯向上取整） | 22,837,991 kg | 4.19% |

其中**只有 1.56% 是选择**；2.45% 由「每轮 2 m 头尾」强制，4.19% 由「只允许整根钢坯」
强制，两者合计 **6.64% 结构性不可约**。若整根取整不损料，成材率上限
`500,935,599 / (509,444,031 + 13,351,098) = 95.82%`；若修边也不损料，上限 **98.33%**。
这是规则下的物理天花板，与算法无关。

**"是否到极限"的三条证据。** (1) λ 扫描的 9 个点里 2400 最优（§6.2），是该定形族内的
解析最优；(2) 把配对窗口从 4 加倍到 8（`runs/pair8`），输出的 **12,559 个回合逐条完全
一致**（回合多重集、每单参与度全部相同），配对启发式已在其参数上达到不动点；(3) `r`
从 0.10 放大 10 倍只换 +0.11 分。三项互相独立地指向同一个解。

### 6.6 主导一切的一项：刀的取整口径（`int(L//size)` vs `nearest`）

本次复核发现的**单项影响最大**的未决事项，量级超过全部 λ、r、配对余量之和。

`solver` 导出方案时写 `round(k × 定尺, 9)`；这个 9 位小数在某些 (k, 定尺) 组合上会落到
整数下方（如 `18.0 / 3.6 = 4.999999999999999`），于是**同一份方案**有两种读法：

| 读法 | 段数 | 总刀数 | 刀分子分 | 总分 (B=90k) |
|---|---:|---:|---:|---:|
| `int(L // size)`（`row_metrics` 的计费口径） | 163,393 | **175,952** | 51.15 | **78.0006** |
| `nearest`（`platform_check` 的收件口径） | 177,782 | **190,341** | 47.28 | **76.4539** |

差异 14,389 刀 = 8.2%，B=90k 下值 **1.55 分**、B=180k 下值 **2.17 分**。六个 `r` 全表
复算（与 §6.3 同源脚本）：

| r | 刀数(floor) | 刀数(nearest) | ΔS(B=90k) | ΔS(B=180k) |
|---|---:|---:|---:|---:|
| 0.02 | 211,356 | 227,047 | +1.177 | +2.354 |
| 0.05 | 178,735 | 192,973 | +1.486 | +2.689 |
| **0.10（交付）** | **175,952** | **190,341** | **+1.547** | **+2.173** |
| 0.25 | 174,994 | 189,519 | +1.577 | +2.009 |
| 0.50 | 174,785 | 189,317 | +1.581 | +1.969 |
| 1.00 | 174,741 | 189,270 | +1.582 | +1.959 |

**两种读法下 `r` 的排序不变**，`r = 0.10` 与最优相差仍 ≤ 0.08 分——§6.2/§6.3 的**选点
结论稳健**；但**绝对分数不可自信引用**：B=90k 时是真 78.00 还是 76.45，取决于平台实际
用哪一种取整。

哪一种更可能？`platform_check` 用 `nearest` 判定交付，而这**几乎是唯一可能的口径**：
若平台对交付也用 `int(L//size)`，则 39.8% 的 (k, 定尺) 组合都会被判「少交 1 件」，
几乎所有方案都会爆违规，显然不成立。既然平台对**交付**必须宽容，它对**计刀**大概率
也宽容，因此 **`nearest`（190,341 刀）更可能是平台的真实口径**。本报告保留两种读法的
全部数字，不单选一个当作官方预测。

我们**刻意没有**去利用 `int(L//size)`：把每段长度写到整数倍下方 1e-15，理论上可使分段
计费归零（刀分子分封顶 100，B=90k 下凭空 +19.5 分），但这是在利用评分器的浮点表示而非
求解优化问题，且一旦平台口径自洽（对交付也 floor），会导致大面积「少交」违规。当前
方案自带的 8.09% 折扣只是 `round(…, 9)` 的**自然浮点落点**，不是刻意构造，也不计入
任何"预期收益"。

## 7. 风险与未决事项

1. **刀数取整口径未确认（影响最大，§6.6）**。同一份方案在 `int(L//size)` 与 `nearest`
   两种读法下相差 14,389 刀（8.2%），B=90k 下值 1.55 分、B=180k 下值 2.17 分——大于
   全部 λ、r、配对余量之和。我们判断 `nearest` 更可能是平台口径（否则交付判定会崩），
   但无法自证。**因此本报告所有"刀数/总分"的绝对值都应理解为区间：B=90k 下
   78.00 ~ 76.45。** 选点结论（`r = 0.10`、λ=2400）在两种读法下均不变；
2. **刀数基准 B 未确认**。复赛未公布 B，初赛为 90000。本报告已给出 B=90k/180k 两种
   假设下的结果，结论一致；但绝对分数不可当作官方预测；
3. **时间子分口径未确认，且同一页 PDF 自相矛盾**：正文为独立 10%，紧接的公式却是
   40/40/20 且无时间项，群答疑又称并入成材率。三种读法都已实测（§6.3），`r` 的选点不变；
   对绝对分的影响上限为 10 分（时间项取满分 100 与取 0 之差）；
4. **超产上限是求解设置，不是官方规则**。题目未给上限；我们依据约束 7/8 的单边下界
   与 `RULES.md` 第 18 行「超产不扣分」使用 `r = 0.10`，并已确认**实际超产量仅 1.56%**
   （名义 10% 只在「再大一档并列支数恰好还落在窗口内」处被用掉，不是每单都顶到上限）。
   若官方另有隐性上限，`r = 0.02` 的备选方案可立即替换（代价 3.34 分，见 §6.2），三层校验同源可复现；
5. **1 个订单未能配对**（`C60:26.5`，构成单订单方案），使覆盖率停在 99.99% 而非 100%；
   代价 `0.2 × 1/9999 ≈ 0.00002` 分（覆盖率子分 99.99 对 100），未进一步优化；
6. **配对质量未做全局优化，但已实测到不动点**。当前为邻接配对（lookahead=4）；重定形使
   刀数几乎与配对无关（`Σ K_i` 只取决于逐单 `P_i`）。实测把 lookahead 加倍到 8
   （`runs/pair8`）后，**12,559 个回合逐条完全一致**（回合多重集与每单参与度均相同），
   方案指标一字不差。故该方向无剩余收益，不必引入全局配对搜索；
7. **异常订单 B20270281** 按异常过滤隔离，未猜测其定尺/重量。若官方口径要求

## 9. 结论

复赛的核心差异不在「多了一条连续性约束」，而在于**评分口径的三处翻转**：
计刀从「每单加头尾」改为「每轮一组头尾」、成材率分子从「含超产」改为「不含超产」、
覆盖率从「同批」收紧为「同轮」。这三处翻转联动地重塑了最优结构：

- 因为**每轮只扣一组头尾**，刀数随「轮数少、并列支数大」急剧下降 —— 原方案按
  「同交付量取最小并列支数」的旧启发式，恰好在反方向优化；
- 因为**超产不计入分子但也不罚分**，需求件数变成「下界 + 2% 窗口」而非等式，
  使「取整边界的自由度」可以被合法变现；
- 因为**覆盖率要求同轮并单**，配对从「越多越好」退化为「两单即可」，
  搜索的必要性也随之消失。

明确这三条之后，可以把问题从「随机搜索 2 小时」重构为「**解析定形 + 双目标选点
1 分钟**」，并在刀数与成材率两个方向同时取得显著改进（刀数 424,000 → 175,952，
成材率 0.823 → 0.918），全部结论均可由三层独立校验与可复现命令复核。

**是否已优化到极限？** 算法意义上**是**：λ 扫描在该定形族内给出解析最优（2400）、
配对窗口从 4 加倍到 8 输出逐条不变（不动点）、`r` 放大 10 倍只换 +0.11 分，三条独立证据
同指一个解。绝对意义上**不是**，但剩下两点都不是"算法没跑到"：一是轮数相对质量下界尚有
42.6% 余量，可实测证明取用它在成材率上是净亏（§6.5）；二是**刀的取整口径**——
同一份方案在 `int(L//size)` 与 `nearest` 下相差 8.2% 的刀数（值 1.55~2.17 分），这是
当前最大的不确定性，且只能由平台反馈、不能由求解消除（§6.6）。成材率轴的天花板由规则
锁死：仅整根坯一项就锁掉 4.19%，加上 2 m 修边共 6.64% 结构性不可约。

**因此本报告对刀数与总分的表述一律给区间**：刀数 175,952（floor 读法）~ 190,341
（nearest 读法），B=90k 对应 78.00 ~ 76.45 分；选点（`r = 0.10`、λ = 2400）在全部
读法下不变。
