## 4. 归因：为什么是「邻域不完备」而不是「目标函数错」

这是本篇最关键的一步推理，请重点挑。

**先看改进的形态**：

- `bi=2255`：`dK=−1, dM=0` —— **省一把刀、材料一分不多**。
- `bi=1764`：`dK=+1, dM=−6,162` —— **多一把刀，换回 6,162 kg 材料**（正好一种最轻坯型的质量）。

**这两类在老目标下是什么符号**？生产搜索用的老目标是 `账单 + KNIFE_KG × 刀数`，
`KNIFE_KG = 2,710.58`（`requant_batches`）：

- `bi=2255`：`Δ = 0 + 2,710.58×(−1) = −2,710.58` → **老目标也认为是改进**。
- `bi=1764`：`Δ = −6,162 + 2,710.58×(+1) = −3,451` → **老目标也认为是改进**。

⇒ **这些招式不是被"汇率差了 40 kg"挡住的，而是根本没有被枚举到。**

**为什么会漏**？`requant_batches.polish()` 的招式集是：每个轮把 count 试到床位上限、`k ± 1`、
**两轮之间的投递安全搬运**、以及删掉整轮。而 `solve_window` 做的是**两轮联合**
（整数段数 × 每个订单在各轮的段数一起重解，用 DP 保证投递与 48 t 下限）。
`bi=2255` 的 `dK=−1, dM=0` 正需要一个**单轮做不到的联合重拆分**——
单轮要么把某订单的投递打破，要么只是买来一把刀。这一点在 `tests/test_blank_step.py::JointMoveTests`
里早就有构造性反例（`test_no_single_round_can_shed_the_billet`）。

**结论（可被推翻的形式）**：`plan_merge2` 是一个**不完备邻域**的不动点。
判据是「这些招式在老目标下也为负」，无需诉诸新旧汇率的 40 kg 差。

> 顺带说明**为什么这不与「汇率不一致」那件事冲突**：精确汇率是 2,670 kg/刀，plan 用的是 2,710.58，
> 一阶错价 1.5%。若把目标函数换成精确汇率重跑，预期位移是二阶小量（已在 `docs/CURRENT.md` 记录）。
> 本轮发现的是**另一个**、量级更大的原因：**邻域本身漏招**。

## 5. 这些改进离「换来新的官方分」有多远（本篇最弱的一环）

**换分门槛**：官方分 = 本地分四舍五入到两位（10 个独立样本，见 `docs/SCORE_MODEL.md`）。
当前本地 92.4751 → 官方 92.48。**要拿到 92.49，本地需 ≥ 92.485，即净增 ≥ +0.010。**

**本轮 15 条能贡献多少**：一阶估计 **+0.0029** → 92.478 → **仍四舍五入 92.48**。
⇒ **单靠这一次窗口=2 普查，换不来新分。**

**那还值不值得做**？依据是 **Wave H 的先例**（`docs/CURRENT.md`）：
Wave H 用"给现有精修器加重启预算"的方式得到 **129 批改进 → +0.03595 分**。
即：**决定增益大小的是改进的条数，不是单条的 dS**。本轮 15 条 × 2e-4 = 2.9e-3；
若迭代能把"窗口招式"的改进条数推到数百条量级，才有希望跨过 +0.010。

**这是外推，不是测量。** 我不知道迭代能积累到多少条——**这正是要跑 `window_ils` 去测的东西**。
如果它收敛时累计仍只有 1e-3 量级，那么本线应当被记为
「发现了一个合法但不足换分的改进，且该邻域已穷尽」。

## 6. 新工具 `window_ils`：把窗口招式迭代到整卷不动点

`blank_step.probe` 只答一次（某个窗口在某个计划里有没有改进）。真正需要的是**反复施加再重估**。

**新增 `tools/analysis/window_ils.py`**，要点：

- **逐轮全量扫**：对每个批，取它所有耦合窗口里 `dS` 最大的那个，施加；
  本批其余窗口留给下一轮（下一轮是新的不动点搜索）。
- **每轮重新绑定汇率**：`rebind()` 把当前计划写到 `tmp/_window_ils_base.json`，
  用 `true_score` 现算 K0/M0。理由与 §2 同源——一轮内施加几十个小改动后，
  拿入口汇率去评价一轮**后半段**的窗口就已经偏了。
- **落地前必过整卷校验**：`plan_check(..., check_delivery=True, weight_mode='strict')` 不过就跳过并打印。
- **三类判定**（沿用 `docs/PLAN.md` 的口径）：
  `APPLIED`（本轮施了 n 条）／`FIXPOINT`（整轮每个窗口都完整枚举、且无改进）／
  `BUDGET`（本轮被时间闸截断 → **未定，不是负结果**）。
- **只在真有改进时才写 `--out`**；否则输入不动。

**冒烟证据**（`--iters 1 --total-seconds 180`）：正确地在 355/2303 批处被预算截断、
`applied=0`、判定 `BUDGET`、**没有写输出计划**：

```
[sweep budget] stopped at batch 355/2303 (180s of 180s) -- UNDETERMINED
sweep 1: applied=0 truncated=0 summed_dS=+0.000000 -> score=92.475076 knives=184494 (181s)
verdict: BUDGET over 1 sweep(s), 181s
```
（applied=0 是**预期**的：15 条改进的最小批号是 591，而这次只扫到 355。）

**成本实测**：≈1,150 秒/轮（**约 19 分钟**），6 小时可跑约 19 轮。

**测试**：`tests/test_window_ils.py`（3 条）——`best_window` 取到联合改进行为 /
无改进时安静返回 / `rebind` 从给定计划取 K0/M0（即 §2 的回归）。
`aic.py test`：**198 通过，跳过 1**。

**已在跑**（09-28 08:53 起，6 小时预算，结束约 14:50）：

```bash
./.venv/Scripts/python.exe -X utf8 tools/analysis/window_ils.py \
  --plan artifacts/runs/requant/plan_merge2.json --data data/semi --round semi \
  --window 2 --iters 0 --total-seconds 21600 \
  --out artifacts/runs/requant/plan_w2_ils.json --json runs/w2_ils.json
```
