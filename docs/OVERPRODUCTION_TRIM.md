# 复赛超产转换（2026-09-26 夜 → 09-27 凌晨）

**一句话**：计划里"多切出来的"片数与申报质量按 1:1 兑换。把 220,141 片超产花掉一大半，
本地预测分 **91.20 → 91.80**（同一结构，未动批次/订单集/刀数上界）；再叠三个新遍历到不动点，
**92.11**（`runs/_rf3.json`，刀 184,521、材 93.65、覆 99.83，零违规）；再叠跨批重打包、共享遍历与
轨迹/循环，本地最高 **92.1572**（`runs/_cy1.json`，刀 184,504、材 93.68、覆 99.98，零违规）。

## 为什么这是纯收益

- 成材率分母是申报质量、无欠交时分子是 Σ 需求 —— **多切的每一片只抬高分母，不抬高分子**。
- 刀数 = Σ 片段 + 轮数；多余的片还挂在片段上（砍一个片段 = −1 刀）。
- 单片兑换率 ≈ **61 kg**（平均 定尺长 × 线密度）；对 184,922 刀的盘面 ≈ 7.4e-6 分/片。
- 起点 `cand_rounded` 的交付超产 = **220,141 片 ≈ 13.5M kg**。

## 三类花费工具（`tools/analysis/shift_cuts.py`）

| 工具 | 动作 | 材料 | 刀数 | 门槛 |
|---|---|---:|---:|---|
| 片段删除（`drop_pieces`） | 某订单在本轮 k→k−1 | −size×count×lin | **−1** | 该订单 slack ≥ count |
| 降 count（`repack_counts` drop 相） | 本轮 count−1 | −(net+2)·lin | 0 | 轮内**每个**订单 slack ≥ 自己的 k |
| 搬 count（`repack_counts` xfer 相） | 同批次内把 1 个 count 从长轮次搬到短轮次 | −(net长−net短)·lin | 0 | 接收轮不跨坯料边界 |

兑换率：片段删除 ≈ **61 kg/片 + 1/count 刀**；count 类 ≈ **38 kg/片、无刀**。
→ **先删片段（顺手买刀），再用 count 花剩下的余量。**

## 流水线与守门

```
coarsen → coarsen_mixed → reshape → drop_pieces → reshape2 → repack_counts → reshape3 → retype_and_requant
        → requantize_cuts → recount_rounds → split_schemes      （后三个 = 09-27 凌晨新增）
```

- 每一相后跑 `reshape_plan`（切分点平移），把新腾出的交付余量再对齐一次。
- 守门：严格校验器必须通过；net ∈ [48,148]；**总代价**（`2,830 × 刀数增量 + 申报增量`）不得上升；
  覆盖率不得下降；included 订单数不变；每方案轮数 ≤ 6；
  count 的每次变化先用精确账单表 `bill(net,c)=⌈(net+2)·c·lin/w − 1e-7⌉·w`（Decimal ROUND_CEILING，
  最终由 `requantize_cuts` 精确写入）预结算，**接收轮跨界整跳 +w ≈ 8,000 kg 的转移一律拒绝**。

## 三个新遍历（09-27 凌晨，`tools/analysis/shift_cuts.py`）

超产转换吃完之后，剩下的余量碎得动不了；能再赚的都是**换轴**的遍历 —— 每一个都不动前一个动过的东西：

| 遍历 | 动作 | 用一次搜索换 | 实测 |
|---|---|---|---:|
| `requantize_cuts` | 每批**统一 count** 重扫 `count ∈ [max(1,min−3), ⌊2000/dia⌋]`，片段大小由交付下限导出（`lay_pieces` 最短路 DP） | 刀数 ↑/↓ 与申报的联立最优 | 91.80 → 91.99（刀 −242，申报 +0.4M） |
| `recount_rounds` | 每轮 count 降到**该轮下限** `c*ₙ = max_o ⌈pieces_o/segments_o⌉`（RMQ 表取区间最大） | 刀数（轮 +35）换材料（申报 −943k kg） | 91.99 → 92.08 |
| `split_schemes` | 在**无订单横跨**的轮边界把方案切成续段，每段自己选坯料重量（区间 DP，`best(i,j) = min_w Σ bill`） | 申报（取整浪费） | 92.08 → 92.11（申报 −441k kg，刀数不变） |

- 三者都只重写 `length_scheme`/`counts`/`blank_counts`/`blank_type`，**订单集与轮数上界留给前一个遍历**；
  `requantize` 与 `recount` 各自要求严格改进（1.0 kg 余量），`split` 要求严格小于单段成本。
- 换算汇率见 [SCORE_MODEL](SCORE_MODEL.md)：**1 刀 ≈ 2,830 kg 等效申报**，所以
  "省 35 轮 + 943k kg" 与 "省 242 刀" 是同一把尺子，`main()` 的总门控按它判。
- 坑：接受条件写"刀数或材料任一下降"会引入**零增量抖动**（每轮重写 1,300+ 批次、净变化 ≈ 0，永不收敛）；
  加 1.0 kg 余量后两轮内停在不动点。

## 混合 count 批次的重切（`coarsen_mixed`，2026-09-26 夜半）

`coarsen` 只吃 count 均匀的方案，trim 之后的盘面里 **1,880 个批次有 1,818 个是混合 count**，
10,349 轮里 10,137 轮在这些批次里 —— 轮数余量大头恰好被这道门挡住。放开它的代价必须自己付清：
重切会移动切分点，混合 count 下每个订单的交付 `Σ_r k_r·c_r` 会跟着变。

**解法：每轮取该轮订单的交付下限。** 记 `c*_o = ⌈pieces_o / segments_o⌉`（订单自己的下限），
重切时令每轮 count = 该轮所有订单的 `c*_o` 的最大值。订单的轮次连续，于是
`Σ_r k_r·c_r ≥ Σ_r k_r·c*_o = segments_o·c*_o ≥ pieces_o` —— **交付下限由构造保证，不靠事后检查**。
又因账单对 count 单调，每轮的最省 count 就是这个下限本身（低 count 还换来更高的 net 上限）。

- 目标函数用分数自己的汇率：省 1 轮 ≈ 2,830 kg 等效申报；`2830×省轮 > 账单增量` 才改。
  （等价物换算见 [SCORE_MODEL](SCORE_MODEL.md)；只用"省轮数>0"当判据会放进 187 个"省轮但材料反涨"的净亏批次。）
- 额外守门：**覆盖率不得下降**（重切可能把共享轮拆开）。实测一条也未被挡。
- 实测：`_iter1`（91.71）单跑此相 → **91.78**；接全管线再收敛 → **91.80**
  （刀 184,922→184,730，申报 544.87M→544.17M kg，覆盖 99.71→99.76）。1 秒跑完（窗口内 DP，早停）。

## 四个坑（全部实测踩过）

1. **用即时锯齿增益选招 → 91.34**：Δ=1 的 count 步大多当步不跨锯齿边界（即时增益 0），但期望为正。
   排序必须用材料节省率，不能用即时增益。
2. **无跨界守门 → 91.47**：接收轮 count 上升会跨坯料边界整跳 +w，账面"赚"了、申报反而涨 2.75M。
3. **精确账单符号写反 → 放行全部不安全转移**：接收轮成本必须是 `tab_s[c+1] − tab_s[c]`（减号）；
   写成加号时账单增益虚高到 12.9M，修复后 2.29M 才合理。
4. **联合算子的浮点预筛符号写反 → 藏起 9 批改进**：账单项符号反了会挡住"省下整根坯料、同时省刀"
   的那类招式。详见下方[「那道浮点预筛的符号写反了」](#那道浮点预筛的符号写反了09-27-下午外部审计指出)。

## 跨批重打包：重排组成只买到 8 轮

规则 10 只禁止一个订单出现在两个方案里，**不规定谁和谁同批** —— 批次组成是一个此前没动过的自由度。
`tools/analysis/repack_batches.py` 把每个 (钢种, 直径) 组内的订单重新装箱、每批从零重切：

- **装箱**：订单按"自身最高 count 下的链长"降序首次适应，每批 ≤ 6×148 m；封口前必须能被切出来，
  切不出来的批把最轻订单退回下一批；链长不足一轮的订单必须与伙伴同批，否则整组回退。
- **重切**：每批重建 count（1..辊道上限全扫，取 5 个短名单真跑 `lay_pieces`），估价用分数自己的汇率
  （1 刀 ≈ 2,830 kg 申报质量）。**拒收链长填不满一轮的 count** —— 这是高 count 端的陷阱：
  片数最少、却切不出任何一轮，早期估价把它排在最前，会让整组"优化"成更贵的方案。
- **门控**：整组重切后按同一汇率比价，更贵就保留原批（36 组里 33 组被保留）。

实测 **92.1087 → 92.1147**（轮 10,218→10,210、刀 184,521→184,510），级联到不动点 **92.1155**。
两条独立谱系（先修 count 窗口、后修估价排序）产出**同字节**的计划——这个不动点是稳的。

### 伪靶：`_repack_sim.py` 的 9,040 轮

早期脚本 `runs/_repack_sim.py` 按"每单最高 count + 长度/床重装箱"算出 10,218 → 9,040 轮（差 1,178），
`runs/_group_floor.py` 给的同组地板 8,658 是同一类下界。两者**都不可及**，因为它们忽略了：

1. **`cap(c)` 与塔高 count 反向走**：一轮最多载 `cap(c) = min(148, 60000/(c·lin) − 2)` 米净长
   （床重 60 t，外加每轮 2 m 修整）。count 越高 `cap` 越低 —— 高 count 省片段（`Σ⌈P/c⌉`），
   却把轮数推上去，而每多一轮还多一份 `2 × count × lin` 的账单。
2. **每交付片的账单，只有连续项与 count 无关**：一轮的账单 `⌈(net+2)·c·lin/w⌉·w` 除以该轮交付片数
   `net·c`。把 `⌈⌉` 拆开，连续项正好约掉 count —— `lin·(1 + 2/net)`，只由轮净长决定；但**取整余项不约**：
   `⌈x⌉·w = x·w + r·w`，`r = ⌈x⌉ − x ∈ [0,1)` 随 `(net+2)·c·lin/w` 变，所以 count 动一点就可能让整轮账单
   跳一根坯料（可上可下）。这个余项既是下面那些"台阶"的来源，也正是 `requant_batches.py` 在 count 上
   找钱的机理 —— **不能据此说 count 整个约掉了**。

实测（`tools/analysis/round_fill.py runs/_rp4.json`，逐轮统计）：

| 事实 | 数 |
|---|---:|
| 轮数 / 平均净长 / 平均 `net/cap(c)` | 10,210 / **96.1 m** / **85.8%** |
| 受床重挡（`cap(c) < 148`）的轮 / 受长度挡 | **9,037** / 1,173 |
| 正好顶到 `cap` 的轮 | **1** |
| 轮距 `cap` 的平均差（中位） | 15.8 m（11.3） |
| **轮距"账单多付一整根坯料"的平均余量（中位）** | **3.1 m（2.5）** |
| 轮距 `cap` 的差 ≥ 距账单整根的余量 | **8,445 / 10,210** |

两行相比就是结论：要填满到 `cap` 平均还差 15.8 m，但**平均只剩 3.1 m 就会跳到下一个整根台阶**，
82.7% 的轮都是台阶先到 —— 净长再加几米就会整跳一根坯料（数千至上万 kg），比多切的那点长度贵得多。
所以这些轮不是"没装满"等在那里：它已经停在账单 `⌈·⌉` 的台阶下沿，
"把每轮铺满到 148 m"既不可达、也不是目标。真正的杠杆是**降低 `(net+2)·c·lin` 让账单掉台阶**
（`requantize_cuts` / `recount_rounds` 做的正是这件事），至于组成重排，整套只值 8 轮。

## 跨批联合重建：在最小的组上实测（09-27 下午，审计 §3）

审计建议"先用小窗口得到高质量结果或最优性界，验证当前批次边界到底锁住了多少收益，再决定是否扩大"，
并称这是唯一一条**可能改变解的结构**的建议。我们在**最小的组**上做了，因为它是最便宜的窗口：
`XL2:38.0` 只有 20 单，整组能塞进一个 chunk（`--chunk 60`），不存在"组内还要切块"的干扰。

现状（`plan_deep1` 里这 20 单的 6 个批）**就是基线**：22 轮、**373 刀**、账单 **1,064,219 kg**、**0 seam**。

| 做法 | 方案 | seam | 轮 | 刀 | 账单 kg |
|---|---:|---:|---:|---:|---:|
| 现状（6 批） | 6 | **0** | 22 | **373** | **1,064,219** |
| 联合从头解（`solve_semi.py --groups XL2:38 --chunk 60`，原子块） | 5 | **17** | 22 | 375 | 1,118,864 |
| 联合从头解（`--chunk 6`，组内重划成 4 块） | 6 | **15** | **21** | 374 | 1,096,432 |
| 接续感知重划分（`repack_batches.py` 喂它这 6 批，完全自由重划） | 6 | **0** | 22 | **373** | **1,064,219** |

四行读完就是结论：**批次边界在这个窗口上锁住的收益是零**；而**凡是求解器"改进"出来的，都带接续违规**。

- 联合从头解把 20 单的自由度用满，**轮数一样是 22**，刀 +2、材料 +54,645 kg，**违反接续规则 17 次**。
  把组内再切细（`--chunk 6`）能拿到 **21 轮**（少 1 轮），代价是**刀反而 +1、材料 +32,213 kg、15 条 seam**
  —— 少的那一轮是用违规换的。（求解器摘要里的 `knives 340` / `333` 是它的 floor 口径，比半决赛口径低约 10%；
  上表是按半决赛口径量的。）
- 接续感知的重划分给的是**逐位相同**的计划，工具自己打印 `the re-grouped plan is not an improvement`。

**为什么是零**：接续规则管的是"相邻两轮共享 ≥2 个订单即违规"，而当前全卷 7,989 条相邻轮边界里
**95.3% 共享订单、每一条上恰好只有一个共享订单坐在接缝上**（全卷 seam = 0）。也就是说这套结构的每个
接缝都是**单订单交班**——联合重建要走的那个方向（把两轮内容揉到一起）**按构造就会产生 ≥2 共享**，
直接被规则毙掉。锁住结构的不是批次边界，是接续规则；边界只是那条规则的一种表现。

**这同时回答了审计的另一问："哪些约束锁住了材料账单"（§3 第 3 条）。** 排在第一的不是批次边界，是三样：
(a) **每轮账单自己的 `⌈·⌉` 台阶**（一轮的余项一动就跳一根坯料，见上文"伪靶"一节）；
(b) **接续规则的"单订单交班"结构**——它把能合并的轮挡在门外，本轮实测的直接证据；
(c) **每方案 ≤6 轮**的上限（挡住剩下的 2 个未覆盖订单，≈0.004 分）。三者里只有 (a) 是算子能撬的，
这也正是 `requant_batches.py` 在 (k, count) 上找钱、并且五波之后收益塌陷到 +0.0032 的原因。

**一个必须记住的坑**：`src/solve_semi.py` 的 `search_10s` **不建模接续规则**（它的合法性模型早于
09-26 那条规则的钉死），所以它才会"赢"着省刀、实际吐出一份 17 seam 的不可行解。任何未来的联合重建
必须建在 `requant_batches.evaluate` 的合法性模型上（它把 seam 记成 200,000 违规，并用 `seam_keys`
修缝），否则就会重演 v4 那次"本地更优、平台 0 分"的陷阱。

**动作**：**不扩大**。这个窗口是最便宜的、也是最可能给出"边界很贵"证据的地方，它给出的是零；
再往上扩组，规模涨、接续规则的约束同样涨，预期收益为负。

## "少一根坯"探针：两轮联合重定量（09-27 下午，`tools/analysis/blank_step.py`）

**它要回答的问题**：材料平台期到底是"现有算子找不到组合"（空间在、算子到不了），
还是"这些批次内部已经没有值得追的组合"（空间没了）？现有算子各占一半：
`transfer` 只搬片段、不动 count；`requant_batches` 的 (k, c) 扫描**一次只解一轮**。
两者都够不到"**两轮同时改 count 和片段分配**"这个方向——而两轮恰恰是这个方向上最小的一步。

**为什么两轮是恰当的尺度（不是图省事）**：全卷 7,989 条相邻轮边界里 95.3% 共享订单，
但**每条接缝上恰好只有一个共享订单**（seam = 0，见上文跨批联合重建）。所以一个相邻两轮窗口里
**最多只有一个共享订单**——它的片段在两轮之间怎么分、加上两轮各自的 count，就是这个窗口的**全部**自由度。
单轮算子拿不到这个自由度（它动不了"跨轮分片段"）；三轮窗口是同一件事的放大版，但枚举空间大得多，
而新增的那点自由度买不到新东西（首版先只做两轮，三条窗口只在两轮有苗头时才展开）。

**固定 vs 可变**（严格按计划划定）：**固定** = 批次组成、轮数、轮序、每轮的订单集合
（于是接缝结构与覆盖率和基准逐位相同 → `dH = 0`）、第一轮的坯料类型；**可变** =
窗口内那两（三）轮的 count、其中**每个订单的片段数**、以及由此导出的申报坯数。窗口只在
`ex_i + ex_j ≤ w` 的**耦合对**上开（见下面的房间筛选），不是所有相邻对。

**判据只有一个**：精确总分增量

```
ΔS(dK, dM, dH=0) = 6,400,000·(1/(K0+dK) − 1/K0)
                 + 40·D·(1/(M0+dM) − 1/M0)          K0 = 184,531   M0 = 536,301,947
                 + 20·ΔH/9999                        D  = 506,157,994
```

**旧的 kg/刀汇率已退役，而且差得不是小数**：精确汇率 = `6.4e6·M0²/(40·D·K0·(K0+1))` = **2,670.00 kg/刀**，
而 `requant_batches.KNIFE_KG`（在 REF_BILL/REF_KNIVES 上线性化的那个）= **2,710.58 kg/刀**。
**一条"多一把刀、省 2,671–2,710 kg"的招式，两个判据给出相反的符号**——实测 `dM=−2700, dK=+1`：
精确 `+2.113e-06`（收）vs 线性 `+10.58 kg-eq`（拒）。探针的代码里只留精确判据（`blank_step.delta_s`），
线性汇率留着当搜索启发式，不参与裁决。这条已写成测试
（`tests/test_blank_step.py::test_the_exact_judge_and_the_retired_linear_rate_disagree_in_a_band`）。

**房间筛选**（`blank_step.py select`）：账单模型给出可判定的充要条件。轮 i 停在它的 `⌈⌉` 台阶上方
`ex_i = used_i mod w` 处；从它搬走 `d` kg，只要 `d ≥ ex_i` 就掉一整个台阶，而接收轮 j 只要
`d ≤ w − ex_j` 就还在自己的台阶上。所以**一对轮能省下一根坯 ⟺ `ex_i + ex_j ≤ w`**，
可用房间 = `w − ex_i − ex_j`，而"跨过去需要几次最小片段搬迁" = `房间 / min(size_o·c)`。
按房间排序把 2,303 批筛成 **100 批**有非负房间的，探针实际就是在这些批上开窗口。

**三类结果**（计划要求的口径，代码逐窗口记 `cls`）：`IMPROVED`（找到合法且总分更高的配置）、
`INFEASIBLE-IN-DOMAIN`（**在枚举域内穷尽**后无解 —— 这是有界证明，不是超时）、
`BUDGET`（枚举被状态数/时间截断 → **未定，不算负结果**）。`solve_window` 是稀疏 DP，
状态是精确净长元组、每状态带片段分配元组，所以"域内无解"是可复核的陈述。**每次 IMPROVED 都跑真校验器**
（`platform_check.check(..., check_delivery=True, weight_mode='strict')`）并用平台已验证的评分器
重算整卷 ΔS；只有 `dS > 0 且 check.passed` 才打印 `CONFIRMED`。本地模型的 bug 只会让我们漏掉候选，
不会造出假候选。

**等预算对照现有精修器：探针的招式被现有算子完全复现，两处还被超过（这一条推翻了第一版结论）**。
第一版对照做错了一步：用 `--iters 200000 --seeds 3`（纯退火，**不带 `--kicks`**）在 `bi=1374` 上跑，

|---|---|---|---|

| `bi=591` | bill −8,134 kg、刀 **+1** | bill −8,134 kg、刀 **+0** | **精修器严格更好**（探针白付一把刀） |

**"效果逐位相同"不是说配置相同**——这正说明探针是特例。`bi=1374` 上：探针把共享订单
`B20270445` 在第 2/3 轮的片段从 `57.6 m + 83.2 m` 改成 `57.6 m + 89.6 m`（把 6.4 m 从 r2 挪到 r3），
两轮 count `45/46 → 43/44`；精修器给的是**同一类联合动作的另一组配置**——
它把 445 的片段改成 `k=9 / k=14`、两轮 count `45/46 → 46/42`。**两者都是"两轮同时改 count 和片段分配"**，
账单与刀数的增量一模一样（−6,162 kg、+1 刀）。也就是说 `requant_batches` 的状态
（每轮每订单的片段数 k + 每轮 count）**本身就是一个多轮联合算子**，
探针只是把它限制在两轮窗口里的一种特例。

`--kicks 200 --merges 200 --merge-depth 3` 的同预算跑，`bi=1374` 仍是同一笔。所以**这不是新能力**：
两轮窗口做到的事，`requant_batches patch` 的重启预算也做得到，而且在三个里的两个上做得更好。

**更强的旁证（Wave H 已经跑出来的）**：Wave H 的**十二个工位**（全体 2,303 批切成 12 片、
每批 400 次重启，六片纯 kick、六片 depth-3 合并）在 `plan_deep1` 上找到 **129 批改进**
（`tmp/_waveh_classify.py` 全量解析），其中 **60 批是"账单下降"**
（正是探针要找的那一类），**69 批是纯刀**。按精确边际汇率折算 **≈ +0.036 分**——
**是探针全部产出（+0.0009）的约 40 倍**，而且和探针用的是同一类招式。
探针独立发现的 `bi=1374`、`bi=494` 两个批，**Wave H 的 `m6` / `m2` 工位也各自找到了**
（`m6 bi=1374` 与探针效果逐位相同；`m2 bi=494` 账单 −6,581 kg，比探针更好）。
**后续 Wave I 接着把预算提到 3×（1,200 重启）并集中在 166 个好批上，只多买到 +0.0069（30 批）**
——见下节，那是这条路的饱和证据。

**结论（按计划的收口口径，且落在计划自己写明的停止条件上）**：计划的停止条件里有
"**收益能被现有算子复现**"这一条，**它成立了**。所以那条开放问题的答案是：

- **"材料平台期来自现有算子找不到组合"——只对一半**。空间确实在（Wave H 一口气找到 58 个），
  但缺的不是**算子结构**（两轮联合并不在现有算子之外），而是**重启预算**——
  这与 Wave H 自己的头对头结论（"卡住中间批次的不是招式种类，而是重启预算"）**是同一句话**。
- **"这些批次内部已经没有值得追的组合"——错**。还有。

**因此：不扩大。探针不是新算子，是现有算子在更小窗口上的一个特例。**
它作为一个**可判定、可复现、有测试的诊断工具**留在树上（`tools/analysis/blank_step.py` +
14 个测试），以后换轮型/换坯料类型时可以立刻用它量"这个方向上还有多少可走"，但
**材料增益的来源应该继续走 Wave H 那条路（给现有算子加重启预算），不是给它写新的联合算子**。
这也正是计划里"两个研究线各自判定、只有一条被证明有效才加预算"的落地：
**有效的是 Wave H 那条**（已实测 ≈ +0.036），探针那条到此收口，**投入不再扩大**。

### 重启预算那条路的饱和点（Wave I，09-27 傍晚）

Wave H 证明"给现有算子加预算有效"之后，计划要求"按实际增益与单位时间成本决定要不要继续加预算"。
Wave I（`runs/_requant_merge2.sh`）就是这一次加预算的实测，也是**这条路的收口实验**：

| 波 | 预算 | 目标批 | 改进批数 | 增益 |
|---|---|---:|---:|---:|
| Wave H | 400 重启 × 12 工位 | 全 2,303 批 | 129 | **+0.03595** |
| Wave I | **1,200 重启（3×）** × 8 工位 | **166 个"有房间"的批** | **30** | **+0.00689** |

**3 倍的预算，只买到第一轮 20% 的收益。** 边际塌陷得这么陡，说明这条路线在 400 重启附近
**已经接近饱和**——再买预算轮不是有效投入。注意 Wave I 的 166 批是**挑出来的好批**
（Wave H 改过的 129 ∪ 两轮普查的 92），**目标质量比 Wave H 更高而收益更低**，
这更坐实了"饱和"而不是"目标没选对"。

**这条路的正确用法因此是"均匀 400 重启一次"，不是"反复加码"**：Wave H 那种
"12 工位 × 400 重启、覆盖全批"的配置是性价比最高的形态，`plan_merge2`（92.4751）
相对 `plan_merge1`（92.4682）的 +0.0069 是这条路的**尾矿**，拿走即可，不值得为它再开一轮。

**一个被真跑出的招式印证的判据**：Wave I 的 `bi=1748` 是**单轮窗口**、用**一把刀换 9,613 kg**。
把它代进两个判据：精确 ΔS 给 **+6.77e-04**（接受），已退役的线性 `KNIFE_KG` 汇率给
**−2700 + 2710.58 = +10.58 kg-eq**（也接受）——但同族的 `dM=−2700, dK=+1` 那类招式
**两个判据符号相反**（精确接受、线性拒绝）。也就是说这段区间里的招式只有精确判据能正确排序，
而生产管线现在用的就是精确判据，**这是那一轮判据升级在真实搜索里的兑现**。

**探针自身产出有多小（合起来也不动官方分）**：三个补丁落在 `bi=494 / 591 / 1374` 三个
**互不相交**的批上（每个 emit 文件恰好只改一个批），叠起来 `tmp/bs_combined.json` → 本地
**92.4331**、刀 **184,534**（+3）、账单 **536,281,487**（−20,460 kg）、真校验器
`passed=True errors={}`；基准 `plan_deep1` 是 **92.4322**。两者**都是 `round(·, 2) = 92.43`**——
**官方分 = 本地分四舍五入到两位**，所以探针的全部合法产出**买不到 0.01 官方分**
（一个窗口 ≈ 0.00025–0.00039 分；按每根坯 0.00043–0.00068 分算，计划里"要凑 0.05 分需 74–116 个"
的量级是对的）。**这个算术反过来正好支持上面的结论**：探针的产出小到连官方报数粒度都够不着，
而 Wave H 用**现有算子**在同一份计划上一次买到 ≈ +0.035——**该加预算的是后者**。

## 从不共享一轮的订单：15 单买到 13 单（09-27 凌晨）

**机制**：覆盖率分子只数**与别人同轮**的订单。`platform_score` 读 `len(set(scheme)) > 1` 才算覆盖，
所以一个独占一轮的订单，不管交付多少钢，都白丢一份 `COVER_BONUS_KG`。"未覆盖"不是"没在计划里"，
而是"从不与别人同轮"——`_rp4` 里这样的订单有 15 个（覆盖率 99.85%）。

前三条遍历都够不着它：`reshape_plan` **按构造跳过单订单批**（它只在两个订单的切点之间挪），
`repack_batches` 的**组级**门控赌的是"一组整体更便宜"，一个批单独能省下的钱会被同组其他批的波动淹掉。
`tools/analysis/share_orders.py` 改成**逐批**动手：

- 从不共享的订单按片数升序排；对每一单，先把**它自己那个批**重切一遍（`cut_batch` 同一订单表），
  再把它的批与同 (钢种, 直径) 组内**链长最接近的 40 个批**逐个求并、用 `cut_batch` 从零切（合并）。

## 轨迹：flag 的开启顺序决定落在哪个不动点（09-27 凌晨）

上面那些分数都出自**一条**轨迹：先 `--min-rounds/--mixed-rounds`，再 `--requant-cuts`，再 `--recount-rounds`，
最后 `--split-schemes`（每个 flag 各自迭代到不动点），然后才是跨批重打包与共享遍历。
92.14 是这条路选出来的，还是这组遍历的地板？`runs/_traj.py <name>` 从同一个起点 `_iter11` 出发
（`fromseed` 除外，它从 `_p_full4` 出发），把同一组遍历按不同顺序各跑到不动点
（`runs/_traj_<name>.log`），落点如下（按分数降序，M/X 之后的顺序）：

| 轨迹 | flag 顺序 | 最终本地分 | 刀 | 覆 |
|---|---|---:|---:|---:|
| **`cyc2`**（`cyc` 的落点再跑第三圈） | **Q → S → R（净变化 0）** | **92.1572** | 184,504 | 99.98 |
| **`cyc`**（`qsplit` 的落点再跑一圈） | **Q → S → R（R 最后）** | **92.1572** | 184,504 | 99.98 |
| `qsplit` | Q → S → R（R 最后） | 92.1554 | 184,505 | 99.98 |
| `rsplit` | 重打包最先，再 S → R → Q | 92.1516 | 184,505 | 99.98 |
| `splitfirst` | S → R → Q | 92.1508 | 184,515 | 99.98 |
| `sfonly`（≡ `splitfirst`） | 先单开 S，再 S → R → Q | 92.1508 | 184,515 | 99.98 |
| `splitq` | S → Q → R | 92.1477 | 184,517 | 99.98 |
| `recountfirst` | R → Q → S | 92.1429 | 184,511 | 99.98 |
| `sharefirst` | 一次全开、共享优先 | 92.1415 | 184,515 | 99.98 |

四条结论：

1. **对照轨迹逐位复现 stored 谱系**（`_rq*`/`_rc*`/`_rf*`/`_rp*` 每步的 `cost_delta` 与分数都对上），
   所以表里的差异是搜索的差异，不是 harness 的。`sfonly` 与 `splitfirst` 同分同刀同覆（`_iter11`
   已是 M/X 的不动点，单开 S 与 [M,X,S] 等价），这条冗余轨迹证实了 M/X 是空操作。
2. **读法：S 放最后最差，R 放最后最好。** `--split-schemes` 放最后的四条（`staged`/`onebyone`/
   `recountfirst`/`rsq`）都停在 92.1402–92.1429；把 S 挪到 Q/R 之前，落点整档跳到 92.15；三个 flag 里
   **R 放最后、S 在 Q 之后**（`qsplit`）最好。机制上讲得通：S 改的是**方案窗口的边界**，Q 与 R
   都是在既定窗口里重解 —— 窗口一固定，`⌈·⌉` 的台阶就把它们锁住了，先分段 = 先给它们更好的窗口；
   而 R（把每轮 count 压到下限）最后跑，等于把前两步腾出的余量再收一遍。
3. **循环还能再赚 0.0018，然后停。** 把 Q→S→R 整条链以它自己的落点 `_qs1` 为输入再跑一遍（`cyc`），
   分数从 92.1554 涨到 **92.1572** —— 增益全部来自第二阶段的 `[M,X,Q,S]`（两轮 −21,520 / −4,628 kg，
   其余阶段 `cost_delta` 全是 0）；第四圈不存在：`cyc` 的落点再跑一遍（`cyc2`）每一阶段都是 0。
   读法：**ALL 的"不动点"只是它自己内部顺序的不动点**（组合不可交换），换一序再走仍能找到活；
   但两级之后整台机器（含重打包与共享）就锁死了，92.1572 是这条轨迹的天花板。
4. **盆地宽 0.0170**（92.1402–92.1572）：92.14 不是这组遍历的地板，而是**一条轨迹的落点**。
   在这台机器上，选对轨迹比再迭代一轮更值钱；下次搜索应从多条轨迹的不动点**集合**里挑最高，
   而不是把单条轨迹迭代到死。`fromseed` 是同一条级联从**另一条谱系的种子**（`_p_full4`，92.0798）出发：
   它能被抬升 0.055 到 92.1344，但抬不进 `_iter11` 盆地 —— 轨迹差在**级联之前**就定下了。

  碎片化挡住，理论可花 174,752 片里实测捕获 ≈ 80%。

## 逐批 (k, c) 重定量：磨平锯齿（09-27 上午，`tools/analysis/requant_batches.py`）

上面那张地板表里唯一没被工具碰过的一项是**锯齿**：`_cy1` 的账单 540,281,579 kg 里，
材料本身（Σ(net+2)·c·lin）只有 523,799,106 kg，**16,482,473 kg 是每轮质量落在坯料倍数上方
（平均 ~1.6 t）攒出来的零头**，其中 **1,083 个批次差 ≥2 根坯料**。`_probe_floor.py` 量出这条靶：
**vs 自有材料 8,649,632 kg（+0.600 分）**。**超产那 5,995,883 kg 不是靶**：`_probe_surplus.py`
证明可删的 k 单位是 **0**（每单余量中位 18 片，一次 count 步要 55–75 片），删一片省 ~370 kg
却要付 2,710.6 kg-eq 的刀，账是负的。

**为什么 count 是免费的**：刀数 = Σk + R，与 count 无关；每轮账单 = (net+2)·c·lin 上取整到 w 的倍数。
所以移动 c 只花两样东西——**交付**（Σ_k_i·c_i 必须仍 ≥ pieces）与**床限制**（c ≤ ⌊2000/dia⌋、质量 ≤ 60 t、net ∈ [48,148] m），
换来的是每轮质量的**相位**。而 `coarsen` 把 c 钉在辊道宽度上限之后就再没有阶段回头看过它
（`requantize_cuts` 只在统一 count 下重扫、`recount_rounds` 只降不升）——这就是本阶段的入口。

**搜索**：逐批模拟退火，状态 = 每轮的 (每单片段数 k, count c)，目标
`Σ bill(m_i, w) + 2,710.6 × 刀数 + PEN × 违规`（kg-eq），**只有零违规状态才算候选**。
算子六种：k±1、c±1、**snap 到本轮的账单相位**（`snap_c`：在 ≤cap_c 且 ≤60 t 的 count 里挑
`bill(m,w) − m` 最小的那个）、轮间转移片段、增删订单、增删轮。

**两条结构规则必须进目标函数**，否则搜索会一路走向非法解——这条坑实测踩过：
只按账单+刀数寻优时，批 89 报出 −12,325 kg 的"改进"，加上下面两条后归零。
- **规则 6**：一个订单的轮次必须连续（不能有洞，跨方案也不行）；
- **缝**：每个轮次边界上共享的订单必须**同时**是左轮的最后一个 key 和右轮的第一个 key
  → 一个边界最多一个共享订单；两侧共享同一订单的中间轮必须是该订单独占。

**割**：一个方案最多 6 轮（约束 4）。搜索想要更多轮时，`split_scheme` 在**两轮订单交集为空**处
切开（切点从右往左取最晚的合法位置），切不动就整批放弃保留原样。key 顺序由 `seam_keys`
从右往左重排——把共享订单挪到左轮末尾、右轮开头，不会扰动它自己右边那条边界。

**`--extra-rounds`：把"再买一轮"直接造出来**。地板表里"多买一轮"的靶是 **1,064 个批次、
净 +3,497,245 kg（+0.243 分）**（`runs/_prize_list.py` 按 `min(账单−地板, w) − (1 刀 + 该轮 2c·lin) > 0` 排）。
但随机插入一轮会让交付账立刻亏掉整轮产量，退火很少跨得过去；`split_starts` 于是直接构造：
**把某单一半的片段挪进紧随其后的新轮**，半单够不到 48 m 地板时从同一轮**整单带过去**几个，
新轮 count 用 `snap_c` 定，交付量与母轮损失大致相当——起点就在可行域边上，退火只做微调。
带过去的整单若在别处还有轮次就会成为孤岛，这类候选由 `structural_ok` 在生成时剔除。

**守门**：与其它遍历同一条——`main()` 严格校验器不通过就拒绝交付；候选写回前 `split_scheme`
保证每方案 ≤6 轮；写出的 `blank_counts` 就是 `ceil((m−1e-7)/w)`，与 `evaluate` 定价的账**逐位相同**。

### 同批的两条捷径被实测否掉（09-27 08:40）

两条看上去免费、其实一分钱都拿不到的路线，省得以后重走：

- **同布局换坯料类型（5 种全试）= 0 kg**。逐批把当前每轮质量按每种 w 重算账单取最小，
  2,275 个批次里**没有一个**能降（`540,281,579 → 540,281,579`）。因为流水线最后一相
  `retype_and_requant` 已经**按同布局**挑了最便宜的坯料；只有重排之后 w 才会换
  （深挖日志里的 `w 5->2` 全是重排带出来的），而那条路 `--w-try` 已经在走。
- **折叠重复轮 = 0 kg**。把同方案内 (k, c) 完全相同的两轮并在一个轮上（count 翻倍、轮数 −1、
  交付不变、账单只会更低）本来是最干净的"白送一刀"，但 **372 组重复轮 372 组全被上限挡住**：
  `coarsen` 早把 c 钉在 ⌊2000/dia⌋（翻倍即越界），剩下的翻倍就撞 60 t。所以"轮数 −1"
  只能靠真正的重排挣，不能靠折叠捡。

顺带量到轮数的结构余量：按 60 t 质量上限，36 个 (dia, steel) 组各自的轮数下界之和是 **8,748 轮**
（现 10,207），即 **1,459 轮的账面余量 = +0.274 分**（150 m 长度上限给的下界更低，6,540）。
但它要求每个组内部把质量按 60 t **完美打包**成更少更长的段，而每段还必须满足连续性、
缝规则与"每方案 ≤6 轮"；退火在各批上能拿到的多是一刀级别的零头（深挖单批最好 +8,381 kg-eq ≈ 3 刀），
说明这段余量的大头是**结构性的**，不是搜索预算不够。

### 第三条捷径也被否掉：整轮删除 = 0（09-27 08:45）

上面那条"轮数余量"最自然的兑付方式是给 `polish()` 加一个新算子：**删掉一整轮**
（把这轮的 k 按 c_j/c_i 放大后并进其它轮，交付只多不少；省一刀 +2,710 kg-eq，再省它
自己那条 ceil 边界的平均浪费 ~847 kg）。它在下降的邻域里是唯一的"改轮数"动作，
退火和转移都做不到，账面看着像白捡。

实测在 66 个抽样批次（整卷 1/60 步长，覆盖 36 个组）上**一次都没被接受**，两边最终
目标值、轮数、刀数逐字节相同（301 轮 / 5,201 刀 对 301 轮 / 5,201 刀），耗时也一样
（0.24 s/批，加不加这个扫描都是 0.8 min/12 线程跑完全卷）。原因不是代码，是结构：

- **接收轮没有余量**。`snap_c` 与精修本来就把每轮质量顶到 ceil 边界上方最近处，
  "ceil 边界以下的空间"早被榨干；并进来的 ~20 t 材料几乎必然把某个接收轮顶过一条边界
  （+7 t），比省下的 2,710+847 更贵。
- **缝规则直接封死最后几轮**。把末轮的订单并进倒数第二轮，会让那一轮"从同一个订单进、
  又从同一个订单出"而它还有别的订单——`evaluate` 的 seam 项（+200000）当场否掉。
  计划里 4.5 轮/方案、每轮 1–2 个订单的形态，正好是最难并的形状。

所以这个算子留在代码里（`polish(..., delete=True)`，默认开；对合法输入只会严格改进，
不改进就原样返回），但在当前计划上不产生任何收益；要兑付那 1,459 轮，只能走
"拆到订单级重排"的大动作，不是增量搜索能碰的。

### 真正找到钱的是"计数 + 件数"联合算子（09-27 08:55，+0.065 分）

删除轮被否掉之后换了个问法：既然单轮内的 1-D 邻域已到不动点，那就**联合**动两个变量。
给 `polish()` 加了"踢一脚再下降"的 ILS（kick → 允许从违规态修复的下降 → 只留更好的），
40 脚 × 66 批，量到 **5 批各白赚一刀**（+2,711 kg-eq，账单一分不动）。把 bi=666 的新旧
状态并排看，机理很清楚：

```
r5: c 72 -> 75,  k={B20275702: 8 -> 7, B20275703: 17}
    交付 B20275702 936->885（需求 883，仍在线上）  B20275703 1224->1275
    账单 55,462 -> 55,462（同一 ceil 桶）        刀数 119 -> 118
```

**单动哪一个都不行**：只丢一片 → 该订单交付掉到 864 < 883（违反交付底线）；
只加计数 → 质量 54,777 → 57,657，账单跳出桶（+6,163）。两个一起动，计数抬高 3
把交付"补"回来一部分，丢一片只掉 51 片交付，而质量仍落在同一个 ceil 桶里 —— 于是
刀数 −1 白得，账单不动。这正是 `polish` 原有三个扫描（c、k±1、转移）都看不见的方向：
前两个是 1-D，第三个是不改 c 的搬运。

于是把它写成**确定性穷举**（不必再靠踢）：对每个 (轮, 订单, Δc) 组合，"最优丢片数"是
被约束逼出来的（丢得越多越省刀、质量越小，取满足交付底线与 48 m/60 t 的最大值），
所以每个组合只需要**一个**候选；用浮点先筛"省下的刀钱是否大于账单增量"，通过了才交给
精确的 `evaluate`。66 个抽样里的 10 批（5 批与踢法重合，另 5 批是踢法没碰到的）合计
**+27,110 kg-eq**，全卷按比例 ≈ **+0.065 分**，代价 ~2 分钟 CPU（踢法要 66 分钟）。
ILS 那条路因此降级为补充探索（`runs/_requant_ils.sh`，只在最优点上再踢）。

### 那道浮点预筛的符号写反了（09-27 下午，外部审计指出）

上面"用浮点先筛'省下的刀钱是否大于账单增量'"就是 `requant_batches.py` 的 `worth_exact()`。
判据来自 `evaluate` 的目标本身：目标最小化 `billed + KNIFE_KG × knives`，而
`knives = Σ k + 1 每轮`（**与 count 无关**），所以一个把某轮件数改 `−dn` 的招式，恰好在该
`bill_delta − dn × knife_kg` 下降时才值得精确估价。原实现把账单项符号写反
（`bill_delta + dn × knife_kg ≥ 0.5`），方向恰好**挡住"省下整根坯料、还顺手省刀"的那类招式** ——
它们 `bill_delta < 0` 且 `dn < 0`，任何符号反了的式子都会拒掉。

实测（全卷 2,303 批，stride 1，`tmp/_prefilter_probe.py`）：修正后有 **9 批**在旧筛选器的
不动点上严格改进、**无一变差**，合计 **18,255 kg-eq ≈ +0.0013 分**（全卷）。单批最大 3,452
（bi=1306 / 1558 / 1699 等：3,452 = 一根坯料 − 一刀）。量级很小 —— **这**不是与榜首差 1.67 分的原因；
审计自己也说清了：真正的差距是"还有哪些解值得搜索"的判断，不是这一个符号。

修正时还带出两个筛子**本来就没算**的项，两个都是被实测逼出来的
（`tests/test_requant.py::JointMoveScreenTests`）：

1. **整轮被腾空时少算一轮的 `+1` 刀**（`frees_a_round`）。筛子只看单轮的账单，看不见"这一招把整轮
   删掉了"。漏掉它 → bi=1800 的合并招式（65 → 62 刀）整条消失，`MergeKickTests` 由绿转红。
   （这类招式的 `dn ≥ 1`：整轮腾空必然意味着它唯一订单的件数归零。）
2. **从违规态修复时筛子整个不成立**。筛子的经济判据只在**在位状态合法**时等于 `better()` 的判据；
   `allow_illegal=True`（合并踢完的修复下降）时 `better()` 要的是"第一个合法态，不管它多贵"，
   拿账单去筛会**挡住恰好能清掉违规的那些招式**。修正是加一道 `cur[3] == 0` 门。

两条都由 `MergeKickTests.test_a_merge_beats_the_descent_on_the_batch_it_was_found_on` 反着守住：
把任一条改回原样，该测试立转红。

### 联合算子差点把覆盖率当零钱花掉（09-27 上午）

联合算子的第一批 200 批样本（`probe_joint_a/b`）合并后只涨 **+0.00495 分**，而它自己的
账单/刀数账是 **+129,046 kg-eq = +0.00895 分** —— 差额正好 **0.0040**，对得上覆盖率：
`_cy1` 是 9,997/9,999，合并计划掉到 **9,995/9,999**。bi=2156 的 `B20279601` 与
`B20279603` 被"丢片"丢成了各自独占一轮的订单，各白丢一份（0.2 × 100/9999 = 0.002 分）。

原因在 `evaluate`：它的交付底线只记 `int(orders[o]['pieces'])`，**没有给覆盖率定价**；
而平台的覆盖率分子只把"与别人同轮"的订单计入（`platform_score.py`：
`if len(set(scheme)) > 1: combined.update(scheme)`）。`share_orders` 遍历整条链才买到的
共享，联合算子一分钟就能还回去两单 —— 更糟的是这条漏洞对**所有**退火/下降遍历都成立，
而本地校验器不会报错（覆盖率是评分项，不是 `error_counts`）。

修法：把与 `shift_cuts.COVER_BONUS_KG = 30000`（约数）同一个量的**精确分数**
`COVER_KG = 0.2 × 100/9999 ÷ PTS_PER_KG ≈ 28,838 kg-eq` 加进 `evaluate` 的目标
（只进 `obj`、不进 `viol`：放宽不会让不该出的方案过校验器，只是让下降自己算清这笔账），
另加 `shared_orders()` 供测试与报告复用。同一 200 批重跑：

| 计划 | 账单 | 刀数 | 覆盖 | 分 |
|---|---:|---:|---:|---:|
| `plan_joint200`（旧的、无定价） | −77,537 | −19 | 9,995 | +0.00495 |
| `plan_joint_fix`（修后） | −76,798 | −19 | **9,997** | **+0.00890** |

**128,299 / 129,039 kg-eq 保住**，只拒掉 bi=2156 那笔 740 kg-eq 的"零钱"（它的收益连半份共享都买不起）。

**全卷实测（同日 09:00–10:20）：40 个补丁、三波搜索、一张表**。修后的 12 工位先在整卷上做
确定性下降（`polish`，436 批改进），再把 prize list 的额外轮 anneal 跑完（490 批改进），
每一步 merge 都按当前目标重评、并要求补丁严格赢过基准批：

1. **旧目标的退火补丁是负资产，守卫把它们变成了正资产**。那批补丁自报的 `val` 是旧目标算的
   （不给共享定价），所以旧 merge 照单全收，换出 −0.064 分；同一批补丁交给新 merge —
   按当前目标重评 + 必须赢过基准批 — 其中 33 个当场判为不够格（`n_flat`），
   于是 `plan_rq_all` 的 40 个补丁里 16 个被拒。**同一批输入、同一批补丁：旧合并 −0.064，
   新合并 +0.187。**
2. **9,997 不是"又丢一份共享"，是买回来的**：`plan_rq_all` 里两个独占订单各有各的账。
   `B20275372`（bi=367）是额外轮补丁**主动**放弃的 —— 它省下的账单超过 28,838 kg-eq，
   按定价就该放弃（若真能更便宜地买回，修后的下降会在下一波自己买）。`B20271919`（bi=1539）
   是唯一一笔"想买也买不起"：该批 6 单 6 轮（上限），要它 1,626 片、单轮 k≤18，

顺带把 `_requant_report.py` 的两处口径修了：kg-eq 行补上覆盖项，并改掉刀项符号

`score ÷ 6.936e-8` 逐位对得上。200 批样本当时把这条算子的全卷估计抬到 ≈ +0.10 分
（66 批只看到 +0.065）—— 全卷实测是 **+0.187**，样本一直低估它。`tests/test_requant.py` 扩到 39 个用例，新增三条合成用例
（同轮同刀同账单、只换轮内归属时两份共享 = 2 × `COVER_KG`；独占订单 `viol == 0`；
单价 = 0.2/9999 的分数恒等式）与一条工作树用例（bi=2156 不再丢共享，bi=22/11 仍照常改进）。

```bash
  --recount-rounds --output runs/_rc1.json --stats runs/_rc1.stats.json       # → _rc2 → _rc3
.venv/Scripts/python.exe tools/analysis/shift_cuts.py runs/_rc3.json --min-rounds --mixed-rounds --requant-cuts \
  --recount-rounds --split-schemes --output runs/_rf1.json --stats runs/_rf1.stats.json  # → _rf2 → _rf3
```

**这条链不能塌成一次调用**：五个 flag 一次开全再迭代到不动点，落的是**相邻的另一个不动点
92.1415**（见下面「轨迹」一节），不是 `_rf3`。92.11/92.14 这条线是**分阶段**走出来的，复现也要分阶段；
`runs/_traj.py staged` 把每一阶段逐步打印出来（并把 `cost_delta` 与 stored 逐位对照）。
`_cand_shift2.json` 由 `cand_rounded` 经同一脚本（`--min-rounds`）产生；
`_iter1.json` 是 `_cand_full7` 的固定点；加 `--mixed-rounds` 后连跑即 `_iter11.json`（= `cand_iter11`）。
其余四条谱系（`_cand_full2/full4/full8/shift2`）用同一条全命令各跑一遍，得到 `_p_*.json`
（92.01–92.08，结构互不相同，作为窗口内的多样性保险）。

`runs/*.stats.json` 保留每一相的计数；`tests/test_shift_cuts.py`（9 个用例）钉住混合重切的交付下限、
`requantize`/`recount`/`split` 三条不变量（交付下限、轮数不升、分数不降）与覆盖率守门，
并在工作树里对真实计划跑一遍严格校验器。
`tests/test_repack_batches.py`（6 个用例）钉住"两个批次共享一条链就该折成一"的合成例、

`tests/test_share_orders.py`（7 个用例）钉住 `lone_orders` 的语义（只报从不与别人同轮的订单）、
一次合并**买卖双方各自的价**（两单转共享、轮数不升、不超床重）、**一份共享正好值 `COVER_BONUS_KG`**
（同订单同钢种、一份共享排布 vs 一份独占排布，差价 = 1 刀 + 1 根坯料 + 2 份共享）、

（订单集不变、共享数不降、价格不升、每一轮仍合法）。

`tests/test_requant.py`（39 个用例）钉住账单的半步语义（整数倍正好记该倍数，不多记一根）、
